# 市场调研与规划复核

- 日期：2026-10-23
- 目的：对照商业与开源产品，检验当前规划与选型是否有问题
- 方法：第三方横评（2026 年中至年末）、各产品公开定价与功能页；价格随区域与时间浮动，只作量级参考
- 结论先行：**设计本身没大问题，但规划有两处押错方向**——把"AI 教练"当主线（红海），以及缺了真正有壁垒的那块算法（自适应 TDEE）。

---

## 1. 市场全景：四类产品，别混着比

| 类别 | 代表 | 卖点 | 价格量级（2026） |
|---|---|---|---|
| **记录器** | Strong / Hevy / Jefit / IRON | 记录快、历史清、可迁移 | $2.99–12.99/月；年费 $24–70；**Hevy/Strong/IRON 有买断 $80–90** |
| **计划库** | Boostcamp | **11,000+ 套现成计划免费**（nSuns / GZCLP / 5-3-1 / Israetel 课表） | 免费为主体，Pro $59.99/年 |
| **算法教练** | Fitbod / Dr. Muscle / Alpha Progression / Arvo | 自动生成或自动调负荷 | $12.99–19.99/月；Arvo €4/月 |
| **营养算法** | MacroFactor / MFP / Cal AI | 自适应 TDEE / 巨大数据库 / 拍照估算 | $71.99/年；MFP $79.99/年 |

**关键认知**：这四类各自都有成熟玩家，而且价格战已经打完。一个新 App 想同时做四类，等于同时和四拨人打。

---

## 2. 六个必须知道的事实

1. **"AI 生成训练计划"不新鲜，而且比我们快。**
   Arvo 的 set-by-set 自适应在 **<500ms** 内完成，还带 MEV/MAV/MRV 容量追踪和 5 套成熟方法论（Mentzer / FST-7 / Y3T / Mountain Dog / Kuba）。我们的模型生成一次计划要 20–60 秒，且只有"通用分化"这一套逻辑。

2. **"按睡眠/恢复调整训练"已经有人做了。**
   Vora 直接读 Apple Watch / Garmin / Oura / WHOOP 的 HRV、睡眠、静息心率来调训练量（$89.99/年）。我们规划的"睡眠 <6h 减量 25%"是它的子集，且数据源更弱（手动填）。

3. **真正的壁垒是算法，不是聊天。**
   MacroFactor 的核心是**自适应 TDEE**：用每周体重趋势 + 实际摄入回归反推你的真实消耗，每周更新目标。它自己把 MFP 的做法称为 "population formula"（人群公式）——**而那正是我们现在的做法**（Mifflin-St Jeor + 固定系数）。

4. **它对"打卡激励"是反着做的。**
   MacroFactor 刻意**不做红字、不做 streak**（adherence-neutral），因为它认为惩罚式设计会导致"断签即放弃"。我们设计了"连续打卡 12 天"和"完成率"，方向相反。

5. **免费层已经卷到极限。**
   Hevy 免费：无限记录 + 4 套计划；Boostcamp 免费：11,000 套成熟计划。**"我们能生成一套计划"在这个市场里不构成理由**。

6. **单餐精度是死路，趋势才是活路。**
   Cal AI 拍照识别菜品准确率约 90%，但热量误差 **15–30%**（看不清用了多少油）。MacroFactor 干脆放弃单条精度，靠"趋势自校正"——你持续低估 200 kcal，算法会从体重趋势里看出来并下调目标。这与我们 07 号文档的判断一致，但我们的 UI 还没跟上（仍在强调单日"计划 vs 实际"）。

## 3. 逐条复核当前设计

| # | 我们的决策 | 判定 | 理由与改法 |
|---|---|---|---|
| 1 | 4 tab、单会话 AI 教练 | ✅ 保留 | 信息架构没问题，比 5 tab 干净 |
| 2 | 现场模式（计时 + 演示 + 逐组） | ✅ 保留，是核心 | 但要向 Strong 学"最少点击"：完成一组应能在 1 次点击内完成 |
| 3 | PR 实时提示 + e1RM 曲线 | ✅ 保留 | Boostcamp/Hevy 都有，属标配；我们的实现方式（保护规则）更克制 |
| 4 | 换等价动作 | ✅ 保留 | 差异化小但成本低，且真实痛点 |
| 5 | **模型从零生成计划** | ⚠️ **改** | 改成 **"选模板 + 微调"**：内置 6–8 套公认方案（PPL / 上下肢 / 5-3-1 / GZCLP / StrongLifts / nSuns / 全身 3 天），AI 负责选哪套、怎么按你的器械与伤病改。**更快、更可信、成本更低**，也避免"生成的计划不如 nSuns" |
| 6 | **AI 双域教练（训练+饮食）** | ⚠️ **降级为主线之一，不是唯一** | Arvo/Fitbod/Vora 都在做 AI 教练。我们真正的空位是 **中餐 + 数据自主 + 不订阅** 这个组合，不是"又一个 AI 教练" |
| 7 | **静态 Mifflin-St Jeor + 固定系数** | ❌ **必须改** | 补 **自适应 TDEE**：周均体重（3 点均线）× 实际摄入，反推真实消耗，每周更新目标。这是全产品最值得做的一件事，比任何 AI 对话有价值 |
| 8 | 连续打卡 / 完成率 | ⚠️ 改语气 | 保留数据，**去掉惩罚感**：断签不清零，改显示"本月 18 天"；不做红字、不做"你已欠 X 次" |
| 9 | 计划 vs 实际（单日热量） | ⚠️ 改重心 | 单日只做"蛋白够没够 + 大概在哪个档"，**周均才做精确对比**；参考 MacroFactor 的 adherence-neutral |
| 10 | BLE 心率带 | ⚠️ **降到 P3** | Vora 走的是健康平台数据（Apple 健康/WHOOP），不是 BLE 直连。我们应先做"手动记一行睡眠/状态"，BLE 永远可选 |
| 11 | 7 步预登记 | ⚠️ 砍到 4 步 | 只留：基础 / 目标 / 伤病 / 器械。经验、饮食限制、作息放"设置"里按需补。7 步会劝退一半人 |
| 12 | 自托管 + 数据在自己手里 | ✅ 保留，是差异化 | IRON 也在打"数据是你的"，说明这个点有市场；我们做自托管更彻底 |

## 4. 三个规划问题

### P1 范围过载（最严重）

现在规划了 18 个界面、7 步 onboarding、三层食物解析、BLE、PR、动态调整、自托管、插件架构。这是一个 3–6 人团队两个月的量。**一个人做，会在第 60% 处停住，且每个功能都半成品。**

**砍法（按"删了最不心疼"排序）**：BLE → 插件 L3（只留接口）→ 深色模式 → 动态训练调整 → 预登记砍到 4 步 → 拍照（已砍）。

### P2 差异化押错

把"AI 教练"当唯一差异化，但它已是红海，且我们做不过 Arvo（方法论 + 500ms 自适应）和 Vora（多设备恢复数据）。

**真正的空位**：`中餐食物库（1677 条，海外产品没有）` + `自适应 TDEE` + `数据在自己服务器/设备` + `不订阅`。这四条组合，市面上没有一家同时做到。

**"不订阅"可以直接打**：2026 年一份横评明确指出七款主流产品里**只有三款提供买断**，其余全是订阅。"买断 + 自托管"是很硬的差异点。

### P3 算法缺了最关键的一块

这是最要命的：**我们用人群公式算热量，然后用 AI 去解释一个可能错 10–20% 的数字。**

应该改成：初始值用 Mifflin-St Jeor（合理起点），第 2–3 周起用自适应算法接管。参考实现逻辑：

```
每周一次 check-in：
  摄入 = 过去 14 天日均摄入（缺失按前值补，剔除异常值）
  体重趋势 = 3 点移动平均后的线性斜率（kg/周）
  真实 TDEE ≈ 日均摄入 − (周体重变化 × 7700 / 7)
  平滑：新值 = 0.7 × 旧值 + 0.3 × 本次估计（避免单周噪声）
  目标热量 = TDEE × (1 + 目标系数)
```

MacroFactor 官方称需要 2–3 周数据后误差可到 **50–100 kcal**（对比人群公式的 10–20% 偏差）。这是可验证的，且不需要模型。

## 5. 选型复核

| 选型 | 结论 | 说明 |
|---|---|---|
| Capacitor 壳（Android 优先） | ✅ 保持 | 记录类 App 无原生性能需求；WebView 足够 |
| 纯静态 + 自绘 SVG 图表 | ✅ 保持 | 体积与离线优先；图表需求简单 |
| 内置中餐食物库 | ✅ 保持，且是差异化 | 海外产品无中餐库；cn-food-mcp 数据可用 |
| 自托管 server.js | ✅ 保持 | 差异点，且实现成本低（已写） |
| **插件架构（L3 能力模块）** | ⚠️ 降级 | 保留 `StorageAdapter`/`DeviceProvider` 接口，**不做插件加载器**。一个人维护不了插件契约 |
| LLM 作为可选增强 | ✅ 保持 | 与"数据自主"一致；但请把 AI 从"主线"降到"解释层" |
| 直接从零生成计划 | ❌ 改为模板优先 | 见 §3 第 5 条 |

## 6. 立场修订：用 AI 提效追商业化，而不是砍到"能做完"

用户明确：**有 AI 辅助，成品要向商业化 App 靠近**。这修正了我上一版"砍到四件事"的保守倾向——但要说清一件事：

> **商业化品质 ≠ 功能多，而是每个已上线的功能都有完整的边界处理。**
> 商业 App 的区别不在"功能列表更长"，而在空态、加载、错误、恢复、迁移、动效这些"没人夸但缺了就掉档次"的地方。

所以策略改成：**功能面按 v1/v2 分，但 v1 的每个功能必须做成完整闭环**，不允许"半成品上线"。

### 6.1 商业化底线（缺一条就不算商业化）

| # | 项 | 判定标准 | v1 必做 |
|---|---|---|---|
| 1 | 首启引导 | 4 步预登记，可跳过，每步说明"为什么问" | ✅ |
| 2 | 三态完整 | 每个列表页都有 空态 / 骨架加载 / 错误重试 | ✅ |
| 3 | 数据迁移 | 支持从 Hevy / Strong 的 CSV 导入（商业化 App 的硬门槛） | ✅ |
| 4 | 数据导出 | 一键导出全量 JSON，可离开 | ✅ |
| 5 | 崩溃恢复 | 杀进程后：训练会话可续、未保存输入有草稿 | ✅ |
| 6 | 离线与同步状态 | 断网可用；常驻"上次同步 / 待上传 N 条" | ✅ |
| 7 | 隐私与合规 | 隐私政策页、数据说明、可清空、无相机权限 | ✅ |
| 8 | 无障碍 | 正文对比度 ≥4.5:1、点击区 ≥44px、图标有 aria-label | ✅ |
| 9 | 动效 | 转场 160ms、勾选 180ms、尊重 reduce-motion | ✅ |
| 10 | 文案集中管理 | 文案抽到单一文件，为多语言预留 | ✅ |

### 6.2 v1 功能范围（四件核心，每件做完整）

| # | 功能 | 完整闭环包含什么 |
|---|---|---|
| 1 | **记录**：现场模式（计时 + 逐组 + PR）+ 动作库 44 个 | 断点恢复、屏幕常亮、换动作、组间休息、总结页、事后编辑 |
| 2 | **自适应 TDEE**：体重趋势反推消耗 | 前 2 周用公式、第 3 周起接管、每周 check-in 卡片、算法解释（可看公式） |
| 3 | **中餐记录**：一行字 → 解析 → 实际摄入 | 三档入口、置信度标记、油量校正、周均口径对比、来源声明 |
| 4 | **计划模板库**：6–8 套内置 + 按伤病/器械筛 | 模板详情、替换动作、导入日程、重新生成（模板重选而非从零生成） |
| 5 | **打卡（周口径）** | 四态、补记 7 天、豁免额度、周结算、日历五态（见 `docs/09-checkin-model.md`） |

> 打卡从"附属功能"提升为第 5 件核心——因为周口径直接影响留存与 AI 数据质量。

**明确放到 v2 之后**：BLE 设备、动态训练调整（睡眠/HRV）、插件 L3、深色模式、分享/社交、动作视频素材、拍照识别。

## 7. 一句话结论

> 我们原来的规划是"用 AI 做一个更好的健身管家"，但 2026 年 AI 管家已经过剩。
> 应该改成"**中餐 + 自适应算法 + 数据自主 + 买断**"——AI 只在需要解释和对话时出场，不再当主线。

设计稿基本可以用，需要动的只有三处：**计划来源改成模板优先**、**热量算法补自适应**、**去掉打卡的惩罚感**。
