# 需求与架构分析（评审意见）

版本：1.0；日期：2026-10-24；状态：**评审意见，不定义 v1 范围**。范围以 [00](00-v1-baseline.md) 为准，本文只回答三个问题：现有需求能否直接开工、架构能否承载承诺、下一步应先补什么。文中 `02:66` 表示 `docs/02-architecture.md` 第 66 行。

> 历史记录：本文“同步契约已落地/问题已关闭”等说法指当时 v1 证据，并不证明后续 v2 删除防复活已实现；当前目标和未通过门禁以[同步契约 v2](sync-contract.md)及[验收](12-v1-acceptance.md)为准。

## 0. 结论

1. **产品方向已经收敛，且比多数同类设计更克制。** 核心任务是"快速记一组 → 可靠保留 → 看见进步"，训练与饮食事实分离、统计口径分离、AI 降为可选输入，这些判断是正确的，应保留。
2. **M0 已部分关闭（2026-10-24 更新）。** `00:74` 要求 M0 交付"内容清单"且"无未定义关键口径"。7 项文档口径阻塞中已关闭 5 项（`slotId`、`FoodLogItem` 父子、`computeWeek` 判空、计入周目标语义、过敏原模型均已在 09/11 增补）；内容清单已建立但过敏原标注与营养策略参数仍缺，因此 M0 仍不能整体签字。另有 3 项契约阻塞未动。按 `00:18`"文档冲突属于开发阻塞"，契约部分必须先裁决再进 M2。
3. **架构的分层方向正确，可靠性契约写到了同类文档少见的深度**（本地事务、持久化 outbox、条件写、三方冲突、不自动 LWW）。真正的风险不在"选错架构"，而在**三个未定契约**：快照物化与规范化哈希、同步分支（datasetId 绑定 / 删除墓碑 / 幂等与条件写顺序）、安全边界（CSP、token、Android 备份与 TLS）。这三处不定，M1 会以"看起来能跑"的形态返工。
4. **容量假设需要先实测再冻结。** 按 11 号字段构造的三年数据集（600 会话 / 36,000 组 / 4,000 餐 / 1,100 体重）实测快照 **24.7 MiB**（UTF-8，gzip 后 3.2 MiB），已占 32 MiB 上限的 77%；若每组再留一条审计则为 **35.3 MiB，直接超限**。若客户端用 `String.length` 预检，中文密集的快照（备注、食物名、动作名）会低估，单条纯中文文本的字节/字符比可达 1.5。
5. **建议顺序：内容清单的两项缺口（过敏原标注、营养策略参数）补完后，做三年数据容量 spike 并冻结 3 项契约 → 再进 M2。** 注意：代码已先行实现 S1–S3（训练记录、周目标、模板编辑、历史更正），文档修正是在事后追平；这违反原定"G0 通过才开代码"的顺序，已在 [QA 报告](qa/2026-10-24-acceptance.md) 记录为流程问题。

## 2. 产品需求分析

### 2.1 定位与范围

- **目标用户单一**：规律力量训练、兼顾中餐、重视离线与可迁移的一般健康成年人。没有同时讨好"增肌/减脂/康复/社交"四类人，这是 v1 能做完的前提。
- **两条路径清楚**：初学者用 3 套模板起步；有习惯者自建或空白训练。且明确"无需先填身高体重即可记训练"（`00:26`、`05:18`），把营养资料推迟到真正需要计算时，这个取舍正确。
- **后置清单明确**（`00:51`）：自适应 TDEE、睡眠调负荷、拍照、BLE、社交、插件平台全部后置，并特别声明"后置不等于不能记录普通工作组"（`00:53`），避免了"为了未来架构而牺牲当下记录"的常见错误。
- **没有把 AI 当主线**（D03）：模板优先、AI 可选、核心记录无账号无 Key 断网可用。这与 08 号市场复核的结论一致，是正确的产品决策。

### 2.2 核心闭环与需求缺口

| 用户任务 | 需求覆盖 | 仍缺什么 |
|---|---|---|
| 今天练什么 | F02 模板/计划、F08 日历 | 模板内容不存在（无内容清单），M0 无审对象 |
| 现场记一组 | F03/F04、05:30–38 | "加/删动作""跳过指定组""休息计时启停"无验收；SetRecord 无组序，无法对应"未录组" |
| 练完看进步 | F05、05:38 | "有效工作组数""力量趋势""上次可比较记录"无统计规则；F05 追踪错配到体重 AC |
| 记录吃了什么 | F06、07 | 六个入口（手工/搜索/最近/收藏/复制/餐单/解析）的默认路径与录入成本未定 |
| 看周是否达标 | F08、09 | "计入周目标"是否需确认与"打卡是派生结果"冲突 |
| 换设备/备份 | F09/F10 | 本地清空在 M1 但唯一 AC 在 M3；配对、初始化合并、解除配对无验收 |

### 2.3 周目标模型：设计最好，但有三处必须先裁决

09 号把"计划 / 执行 / 派生统计"三分、顺延不扣分母、豁免无额度、零目标周不增连续周、补录可重算——这些都比旧四态与 60%/80% 阈值正确。问题在边界：

1. **`goalCreditConfirmed` 的默认值**（`09:7` vs `09:46` vs `11:27`）。如果每次结束都要用户勾"本次计入周目标"，现场多一步操作，和"快速结束"冲突；如果默认计入，则 `goalCreditConfirmed` 不是"仅由用户确认写入"。建议：完成全部计划组时默认计入且不询问；只有低于计划或未关联时询问。这需要产品明确。
2. **`minimumTarget` 的基准**（`00:88` vs `09:19` vs `11:51`）。当某周发生项数 ≠ 用户设定次数（计划周中生效、临时加项），T 取哪个值没有规则，直接影响 K、D 与连续周。
3. **无 goal 周的伪代码顺序**（`09:80` 先取 `goal.currentMinimumTarget`，`09:84` 才判空）。W05 正是无计划输入，按字面执行会抛错；且返回值 `originalPlanned` 与实体 `originalPlannedCount` 不同名。

另外，部分生效周（周三生效，N 是否只剩半周）与 `paused` 周是否中断连续周（`09:99` 两句话都可解读）也未裁定，建议在 09 补一张"边界周"决策表。

### 2.4 饮食与营养

- **"实际 / 计划 / 缺失"三分是正确的产品底线**（07:7）：餐单只是参考，照餐单吃必须显式复制为 FoodLog；未记录不等于 0；`complete` 在增改删后失效。这避免了竞品最常见的"计划当执行"错误。
- **范围克制**：v1 不做自适应 TDEE、不做后台油量学习、不做自动补偿（07:36），只保留静态公式 + 手工目标 + 趋势展示。对一个尚未验证输入质量的 v1，这是对的。
- **缺口 A：输入字段与策略实体。** 07:24 要求年龄、身高、体重、性别参数、活动水平，但 `Profile.nutritionInputs?`（11:21）没有结构；07:28 要求的版本化 `NutritionPolicy` 在 11/03 中都没有实体。AC-N06 因此没有可验证的存储来源。
- **缺口 B：过敏原不可实现。** 07:32 要求"确定性过滤全部原料，无法验证则不建议"，但 `FoodDefinition`（11:33）只有 `nutrientsPer100g`，没有 `ingredients[]`/`allergens[]`；Profile 也没有素食程度与"不吃的食物"。这条安全承诺目前是空头支票，M2 前必须补数据模型或明确降级为"仅提示、不承诺过滤"。
- **缺口 C：录入成本未定义。** 训练侧有"单组记录耗时"指标（00:66），饮食侧只有"全天覆盖率"。若采纳 06 号"只记热量与蛋白、精度换依从性"的建议，就应把手工两项作为默认入口，搜索/解析作为增强；现在的六个入口并列会让首版 UI 失焦。注意 06 号是历史调研（00:18），这里只是借用其取舍逻辑，不改变 07 号"三项完整才校验一致性"的规则。

### 2.5 指标与验证：存在结构性矛盾

`00:66` 定义了首次训练完成率、二周/四周留存、单组耗时、保存恢复率、饮食覆盖率、同步恢复率，但同时规定"用户内容默认不上传作为遥测"。**没有遥测就无法计算留存与完成率**，仅靠"自愿反馈"会得到严重自选择样本。建议二选一并在 00 写清：

- 方案 A：本地统计 + 用户主动导出匿名汇总（可验证、隐私友好、样本有偏）；
- 方案 B：默认关闭的匿名遥测，首次启动明确征得同意（样本完整、需要隐私说明与合规审查）。

无论哪种，都应给出目标值与基线建立方法；现在的指标只有名字，没有判定线。

## 3. 架构设计分析

### 3.1 总体评价

分层 `页面 → 应用命令/只读查询 → 领域规则 → 端口 → 适配器`（02:15–29）是正确的，且明确"领域纯函数不碰 DOM/fetch/存储""视图不持有可变 state""只有事务完成才提示已保存"。这三条恰好对应 demo 的三个病根（全局可变 `state`、`save()` 同步返回 true、404 静默回落），说明架构是从失败中总结出来的，不是模板套用。

可以保留：单体前端 + 可选单体服务、Capacitor/PWA 复用业务代码、IndexedDB 默认存储、整份快照同步（在 v1 规模下比实体级同步更简单）、无微服务/CRDT/多用户。

必须补：快照物化与规范化、同步分支、安全控制、测试基础设施、工程 ADR。

### 3.2 本地事务与 outbox

02:33–35 的意图正确：业务事实、审计、generation、outbox 同事务；成功只确认"实际发送的 generation"，更晚的写仍 pending。但缺三个可执行细节：

1. **快照在何时物化。** outbox 只存"意图"（11:80），若发送时现读现序列化，可能把 G+1 的字节按 G 确认，静默丢一组；若每次写都存整份快照，36k 组会产生巨大写放大。建议：提交事务内写 `generation` 与 `snapshotHash`，由单飞的上传器在只读事务中按 generation 物化，物化时校验 generation 未变，否则重试。
2. **IDB 事务内禁止 await 非 IDB Promise。** 02:27 的 `CommitResult` 没有约束这一点；一次 `await fetch` 就会让事务提前 auto-commit。应写进契约与 lint 规则。
3. **同步租约缺 TTL/续期/fencing。** 02:39 只说"数据库租约与事务校验"；多标签页/多设备接管时，旧持有者仍可能写入。建议租约带 `holderId/expiresAt/fencingToken`，写入时校验 token。

### 3.3 同步协议：分支覆盖表

| 分支 | 文档现状 | 缺口与后果 |
|---|---|---|
| 首次初始化 | `If-None-Match:*`，仅 `DATASET_EMPTY` 可初始化（02:62） | 未定义 `datasetId` 绑定；PUT 是否拒绝 `Dataset.id ≠ 服务端绑定` 不明 |
| 远端已有数据 | 预览"打开为独立数据集或合并"（02:45） | 未说合并走三方合并（02:72）还是导入合并（11:94）；本地分区如何建立不明 |
| 条件写冲突 | 412 → 三份 ConflictCopy → 预览（02:70–76） | 未定义规范化内容，无法判断"一边未改变"；副本保留上限/GC 未定 |
| 删除 | DELETE 清主数据/备份/旧幂等（02:82） | **无服务端墓碑**，`If-None-Match:*` 无法区分"从未存在"与"已删除"，离线旧设备可复活数据 |
| 幂等 | 同键同请求返原结果，异内容 409，保留 7 天（02:64） | 未定幂等与条件写的**校验顺序**；首次 PUT 响应丢失后重试可能变 412，生成"自己 vs 自己"的冲突 |
| 读取 | GET 200 快照 + ETag（02:58） | 无 `If-None-Match/304`、无增量、无定期拉取；每次启动可能下 30MB；"已同步"可能只是"本机无 pending" |
| 跨域 | 默认同源，Capacitor 来源白名单（02:90） | 未定义 `OPTIONS`、`Allow-Headers`、`Expose-Headers: ETag`；Android 页面 origin 为 `https://localhost`，跨域同步会整体失败 |
| 认证 | Bearer，token 不写 URL（02:53） | 未定熵/长度、服务端是否存哈希、常量时间比较、限速、轮换、按设备撤销、读/写/删分权 |

**已落地（2026-10-25）**：约定见 [同步契约 v1](sync-contract.md)，实现为 scripts/sync-server.mjs + src/domain/snapshot.ts + src/domain/sync.ts。原建议保留如下：OpenAPI 3.1 + 快照 JSON Schema + 错误码表 + canonical JSON 规范，客户端与服务端共用一套契约测试。否则 404/409/412/428 会在真机上互相打架。

### 3.4 容量实测（本次新增证据）

按 11 号实体字段构造三年数据集（固定种子，非真实用户数据）：

| 变体 | 会话 | 组 | 餐/条目 | 体重 | 快照 UTF-8 | gzip |
|---|---|---|---|---|---|---|
| 基础（无审计） | 600 | 36,000 | 4,000 / 16,000 | 1,100 | **24.7 MiB** | 3.2 MiB |
| 每 10 组一条更正审计 | 600 | 36,000 | 同上 | 1,100 | 25.7 MiB | 3.5 MiB |
| 每组一条审计 | 600 | 36,000 | 同上 | 1,100 | **35.3 MiB（超 32 MiB）** | 5.8 MiB |
| 压缩快照（仅必要字段） | 600 | 36,000 | 2 条/餐 | 1,100 | 18.5 MiB | 2.3 MiB |

同机（Node 22，桌面）序列化 404 ms、解析 368 ms、进程堆约 162 MB。合成数据以 ASCII 字段为主，整份快照字节/字符比为 1.02；但单条纯中文文本（食物名、备注、动作要点）的字节/字符比可达 1.5，备注越长偏差越大。

结论：
- 32 MiB 上限在"基础"形态下只剩 23% 余量，任何"每组审计/更长备注/更多食物条目"都会顶到上限。**必须在 M1 前做一次真机容量 spike**，再决定：提高上限、gzip 传输、分片上传，还是把审计改为增量。
- 客户端"预检"若按 `String.length` 计算，会低估中文文本（单条纯中文文本字节/字符比可达 1.5，备注越长偏差越大）；必须按 UTF-8 字节或 `Blob.size`。
- 三份冲突副本（11:82）在基础形态下约 74 MiB，两次冲突即 150 MiB，低端机会 OOM；需定义副本保留上限与"仅保留最近 N 次冲突"的 GC。

### 3.5 安全：原则正确，控制缺失

02:86–90 的原则（密钥与业务分离、默认 127.0.0.1、Bearer、no-store、静态白名单、无通配 CORS）是对的。但以下控制没有落到文档，属于"承诺无法验证"：

| 威胁 | 现状 | 缺口 |
|---|---|---|
| 存储型 XSS | 无 CSP/Trusted Types/innerHTML 禁令；模型输出与导入文本（FoodLogItem.label/originalText）可渲染 | 一条恶意食物名即可读 IndexedDB + token 并外传；"本地优先"不等于安全 |
| token 泄露 | 只规定不进快照/导出/日志 | 无轮换、无按设备撤销、无读/写/删分权；一次泄露永久可读可删 |
| 日志泄露 | "敏感正文不进普通日志" | 无 logger 端口、脱敏字段表、保留期；AC-C02 只能人工 grep |
| Android 备份 | 目标文档未提；demo `allowBackup="true"` | Auto Backup 会把 WebView IndexedDB 上云；换机恢复后 Keystore 密钥不随备份，密文解不开 |
| 局域网 TLS | "远程访问使用 HTTPS" | 家庭 LAN 用 IP 访问时证书如何处理？自签证书下 PWA 无法注册 SW；用户会关校验 |
| CORS 预检 | "Capacitor 来源在白名单" | 未定义 OPTIONS/Allow-Headers/Expose-Headers，Android 同步会失败 |

建议：PWA 用响应头 CSP、Capacitor 用 HTML meta CSP；所有用户/模型/导入文本一律 `textContent`；token 支持轮换与分权；`allowBackup=false` 或 `dataExtractionRules` 排除 IDB/密钥；明确"域名 + ACME"或"本地 CA + networkSecurityConfig"二选一的 TLS 方案。

### 3.6 数据模型缺口

除 2.4 的营养缺口外，以下会直接影响实现：

1. **`datasetId` 作用域**：11:9 说分区存储，但实体表都没有该字段；`WeekGoal` 的"同一周唯一"、体重"每天一个"在多数据集下会误判。
2. **`slotId` 未定义**：11:51 用它做发生项唯一键，PlanTemplate/PlanVersion/PlannedOccurrence 都没有该字段，未来 4 周补建幂等无法实现。
3. **`FoodLog.items[]` 与 `FoodLogItem` 二义**：后者没有 `foodLogId` 父引用，删除/同步/tombstone 语义不明。
4. **快照 schema 只有字段名**：`definitionSnapshot`、`workoutSnapshot`、`plannedSetsSnapshot[]` 无内部结构；`SetRecord` 无 `order`/计划组引用，无法把"未录组"对应到具体计划组，AC-T02 的"逐字段不变"无法判定。
5. **删除/级联未定义**：删会话是否级联删组、删 FoodLog 是否删条目、被历史引用的动作/计划版本能否删。
6. **动作版本身份**：`exerciseId` + `definitionVersion` 的 PR 键，与"有历史后改模式创建新版本"的 ID 规则未对齐（换 ID 会断 PR 历史）。
7. **枚举缺失**：食物单位、经验/器械、来源（source）、`nutrientsPer100g` 结构。
8. **`NutritionTargetVersion` 生效区间**：只有 `effectiveDate`，没有"取 ≤ 业务日期的最近版本"的解析规则，历史目标不变无法验证。
9. **审计增长**：11:41 的 AuditEvent 追加不可变，但没有字段上限/归档策略；结合 3.4 的实测，这是快照超限的主要变量。

### 3.7 交付与工程基线

- 04 号对真机、签名、升级、隐私材料的要求是合理的，但**工程基线只停留在文字**：仓库无 `tsconfig`、无构建配置、无测试、无 CI；`package.json` 只有 Capacitor `^7.0.0` 浮动依赖和四个拷贝脚本（`scripts/make-www.js` 是手写 copy，不是构建）。
- `02:8` 说"TypeScript、模块化构建与自动化测试为工程基线"，但没有对应的 ADR 或目录约定；M1 开工前至少要补 6 份 ADR：构建/TS/lint、测试栈/CI/依赖锁定、IDB schema/索引/迁移/配额、同步线协议、Android 工具链/备份/网络安全配置、密钥与日志脱敏。
- 12 号的 D/C/E/P 分层是好的，但缺夹具与工具：三年种子数据生成器、fake-indexeddb、Playwright、adb 强杀/升级脚本、网络故障注入、OpenAPI 契约测试。没有这些，AC-A01、AC-D01/D02、AC-S05/S06 实际不可执行。
- 性能门禁不可度量：20 次冷启动报 P95 接近最大值；"首个可交互训练入口""录组本地事务可见确认"没有判定点；没有快照序列化/上传/内存峰值阈值。建议 ≥100 次采样、P50/P90/max、PerformanceObserver 标记、明确的交互定义。
