# 调研文档：openGym 的架构与产品形态，以及它对「铁馆」的参考价值

- 文档性质：技术调研（不含实现）
- 调研对象：`DuarteSantos8/openGym`（自托管健身追踪器），横向对比 `wger` / `SparkyFitness` / `FitTrackee` / `Sanotsu/free-fitness`
- 调研日期：2026-10-22
- 对应项目：铁馆（`X:/doc/workbuddy/sport`）
- 信息来源：项目 README、仓库提交记录、第三方目录站与对比文章；标注「待核」的条目表示仅单一来源

---

## 1. 一句话结论

openGym 值得参考的是**三个结构决策**（逻辑下沉为纯函数层、存储与后端可替换、同源同端口交付），以及**两个产品形态**（PWA 可安装 + 整份 JSON 即备份）。它不值得参考的是前端框架选型和认证方案——那是它为解决自身问题（1900 行手写 DOM 出现重渲染卡顿、多设备 passkey 登录）付的代价，不是通用最优解。

它的**代码一行都不能抄**：2026-07 许可证从 MIT 改为 **AGPL-3.0**（提交记录明确写「阻止闭源/商业 fork」），并且动作媒体加了 `Cross-Origin-Resource-Policy: same-origin`，注释说明「素材仅授权给 openGym 使用」。可借鉴的是结构与契约，不是实现。

## 2. 事实清单（可核验）

### 2.1 技术栈与分层

| 层 | 实现 | 关键事实 |
|---|---|---|
| 前端 | React 19 + Vite + React Router(Hash) + Zustand | 构建成静态文件，**在 Docker 里构建**，本地不需要 Node 构建链 |
| 领域逻辑 | `frontend/src/lib/` 下的**纯函数**，测试同目录 | 渐进规则、1RM、训练记录回读全部可单测，不依赖 DOM |
| 后端 | `api/` 纯 `node:http`，**只有两个依赖**：`@simplewebauthn/server`、`web-push` | 全部数据以 JSON 存在 `./data` |
| 交付 | `web/` 用 nginx 发静态文件并反代 `/api` | **同源同端口**——passkey 的 RP ID/Origin 绑定要求 |
| 契约 | `api/openapi.yaml`，有可浏览文档页 | 第三方可据此集成 |
| 媒体 | 动作图/GIF 抽到 `./media`，独立 location | 带 CORP 头，禁止外站引用 |

### 2.2 功能面（与铁馆相关的部分）

- 动作库 **5600+**，带动画演示、按肌群在人形图上浏览、按自有器械过滤
- 四套起步计划（推拉腿 / 上下肢 / 全身 / 5×5），加载后是**普通可编辑计划**，不是黑盒模板
- **渐进规则**：线性 / Greyskull LP / 双重渐进（可见次数区间）/ 三重渐进（次数→组数→负荷）/ 加时间；每个目标值都**解释为什么是这个数**；掉次数不加负荷，停滞触发 deload
- **1RM 估算**及曲线、**结构平衡比例**（Poliquin / Thibaudeau / ATG）、一年活动热图
- **肌肉地图三视图**：训练量去了哪 / 哪些还在恢复 / 哪些荒废
- 组类型：递减组、休息暂停、超级组、计时动作、金字塔组；**杠铃片配重换算**（含 EZ 杆、六角杆、史密斯）
- RIR / RPE 可选记录；单侧次数；训练中屏幕常亮；休息计时器
- 导入 FitNotes / Strong / Hevy（CSV 或 API key）、Apple Health 体重；整份 JSON 导出
- 双设备同时编辑 → **字段级合并**而非互相覆盖
- 19 种语言（含繁中），动作名与说明也翻译
- **可选** AI coach：自己服务器的 provider key（Anthropic / OpenAI / Gemini / 兼容端点 / Ollama），**每一处改动需人工批准**；另有只读 MCP server 供外部助手查询训练史
- 可选管理员面板、邀请制注册、审计日志

### 2.3 许可与合规

| 项 | 状态 |
|---|---|
| 应用代码 | **AGPL-3.0**（2026-07 前为 MIT，改动理由写明防止闭源商业 fork） |
| 动作媒体 | 注释说明「仅授权 openGym 使用」，并加 CORP 阻止外嵌 |
| 网络条款影响 | 修改后以服务形式对外提供，服务端代码须开源 |
| 结论 | **只能读结构，不能复制代码/素材** |

## 3. 它的取舍分析（为什么这么选）

| 决策 | 表面理由 | 真实权衡 | 对铁馆是否成立 |
|---|---|---|---|
| **JSON 文件当数据库** | 数据在自己机器上、拷文件就是备份 | 写入频率低（一次训练几十条）、单用户/家庭规模 → 换来零运维。代价：并发写、跨实体查询、多用户隔离全靠应用层 | **部分成立**。铁馆数据量更小（一天十几条），但「多设备同时写」会直接冲突 |
| **逻辑下沉 `lib/` 纯函数** | 便于测试 | 训练规则是产品命脉，必须能在没有浏览器的情况下验证 | **完全成立**，且成本最低 |
| **同源反代 `/api`** | passkey 的 Origin 校验 | 单端口 = 部署简单、无 CORS、Service Worker 作用域干净 | **成立**（与 passkey 无关也成立） |
| **PWA 而非原生** | 一套代码、安装成本低 | 换来离线可用 + 主屏安装；代价是 iOS 上后台能力受限 | **成立** |
| **passkey 登录** | 无密码、不依赖邮件服务 | 必须 HTTPS + 域名，多设备需配对码/二维码 | **当前不成立**——铁馆是单用户、数据本来就在本机，加认证是负收益 |
| **React 重写** | 1900 行 vanilla SPA 手写 diff 导致卡片卡顿（GIF 在勾选 set 时停住） | 换 React 解决的是**该项目的具体性能病因**：大量动画媒体 + 频繁局部更新 | **不成立**。铁馆是视图级整块重渲染、无动画媒体、单页数据量 <200 条，瓶颈不在这里 |
| **5600 动作库** | 覆盖度即竞争力 | 需要持续的素材授权与翻译投入 | **不成立**。铁馆走的是「44 个动作精讲」路线，靠讲解深度而非数量差异化 |

## 4. 与铁馆的逐项对照

| 维度 | openGym | 铁馆现状 | 判定 |
|---|---|---|---|
| 交付形态 | Docker Compose / 自带服务器 | 双击 `index.html` 即用；可静态托管 | 铁馆更轻，但**缺「自己的服务器」这一档** |
| 分层 | 视图 / lib 纯函数 / api / web | 视图 / engine / store / llm（store 里混了业务） | **有差距，值得补** |
| 存储 | 服务端 JSON 文件（`./data`） | 浏览器 localStorage | 差距明显：换设备/清缓存即丢 |
| 多设备 | 字段级合并同步 | 无（靠导出/导入 JSON 手动搬） | 差距明显 |
| 离线 | Service Worker + PWA | 无 SW，但纯静态本身可离线（file:// 打开） | **半差距**：缺可安装、缺缓存策略 |
| 认证 | passkey（WebAuthn） | 无 | 无需补（单用户） |
| 动作库 | 5600+ 带媒体 | 44 个，含步骤/呼吸/错误/替代 + 肌群 SVG | 路线不同，**不追数量** |
| 训练闭环 | 渐进规则 + 1RM + 肌肉地图 | 计划生成 + 打卡，**不会自动加负荷** | **有差距，且是产品价值缺口** |
| 饮食 | 营养成分记录（Open Food Facts 生态） | BMR/TDEE + 宏量求解 + 餐单生成 | 铁馆更强（有求解器） |
| AI | 可选 coach（人审改动）+ 只读 MCP | 教练/营养师双身份 + 计划生成 + 一句话打卡 | 铁馆更强（AI 是主线而非附加） |
| 许可 | AGPL-3.0 | 自有 | 不受影响 |

**结论：铁馆不缺功能想法，缺的是「数据放在哪」和「逻辑放在哪」这两件事的工程答案。**

## 5. 值得抄 / 不值得抄 / 抄不了

### 5.1 值得抄（按性价比排序）

1. **逻辑下沉为纯函数层**——`core/` 放日程构建、连续天数、依从率、配餐求解；不碰 DOM、不碰存储。收益：可直接用 Node 跑断言，回归成本近乎为零。（铁馆已有 `engine.js` 这个雏形，但 `store.js` 里仍混着日程构建与统计）
2. **存储适配器化**——视图只认 `load/save/flush` 三个动作，底层是 localStorage 还是 HTTP 由适配器决定。收益：不解散「双击即用」形态的前提下，多出「自托管」一档。
3. **同源单端口交付**——服务端同时发静态文件与 `/api`。收益：无 CORS、Service Worker 作用域干净、部署只需一条命令。
4. **整份 JSON 即备份**——导出/导入一个文件，附时间戳备份轮转。收益：误操作可回滚，迁移成本为零。
5. **PWA 外壳**——manifest + SW 预缓存 + 启动图标。收益：手机上装到主屏，断网可用。
6. **契约先行**——先定 `GET/PUT /api/state` 的语义与错误码，再写实现。
7. **AI 改动需人工确认**——它的 coach 只提建议、由用户批准。铁馆的「一句话打卡」可对齐这个原则：模型只产出**候选勾选**，最终由用户/确定规则落库。

### 5.2 不值得抄

- **React/Next 重写**：解决的是它自己的渲染卡顿，铁馆没有这个病。引入构建链会让「双击即用」这个优势消失。
- **passkey**：单用户本地场景，认证不解决任何真实威胁，只增加 HTTPS 前置条件与设备配对流程。
- **Docker 作为唯一交付**：可以加，但不能成为默认；铁馆的默认形态应保持零依赖。
- **5600 动作库 + 动画媒体**：素材授权与体积成本高，与「精讲 44 个」的定位冲突。

### 5.3 抄不了

- **代码本身**（AGPL-3.0 + 网络条款）。
- **动作媒体**（CORP 头 + 授权声明，明确仅限该项目）。
- **它的字段级合并同步实现**——可以借鉴「字段级而非整份覆盖」的思路，实现必须自研。

## 7. 采纳建议

| 优先级 | 动作 | 理由 | 风险 |
|---|---|---|---|
| P0 | 逻辑分层 + 存储适配器 + PWA 外壳 | 不改部署形态、可逆、立刻消除「换设备丢数据」的单点 | 低 |
| P1 | 自托管服务端（单端口 + JSON + 备份轮转） | 补齐「数据在自己服务器」这一档，工作量 < 1 天 | 中：冲突策略未定 |
| P2 | 契约化（OpenAPI + `schemaVersion` 迁移） | 为将来的多端/第三方集成留口 | 低 |
| P3 | 数据源升级（中国食物成分表、动作 SVG 素材） | 直接提升专业度 | **中：素材许可需逐项确认** |
| 不做 | React 重写、passkey、动作库扩容 | 与定位冲突或收益为负 | — |
