# 打卡模型：从"每日二值"到"周口径 + 四态"

- 日期：2026-10-23
- 起因：用户指出打卡要保留，但必须**动态**——周内可补某天、有正当原因可缺卡
- 影响：`docs/02` 数据模型、`docs/05 §5.1 / §5.8`、结算引擎

---

## 0. 旧设计错在哪

原设计：当天事项勾完 → 打卡 → 连续天数 +1。

| 问题 | 真实后果 |
|---|---|
| **断签即归零** | 出差一周，前面 12 天白费。这是健身 App 最典型的流失点 |
| **按天算，但计划按周排** | 周三没空、周六补练，系统记"两天异常"，用户觉得被冤枉 |
| **没有"正当缺席"的表达** | 生病了要么硬练，要么干脆不打开 App |

---

## 1. 核心改变：打卡单位从「天」变成「周」

一个计划周有 N 个训练日。**只要本周完成次数 ≥ ⌈N × 0.8⌉，本周即达标**，不管分布在哪几天。

- 周三没空、周六补上 → 系统按周自动算，**用户不需要做任何"补卡"操作**
- 周内某天可显式标记「顺延」（moved），把它当作已安排到别处

---

## 2. 四态模型

| 状态 | 含义 | 谁设置 | 计入达标 | 计入分母 |
|---|---|---|---|---|
| `done` | 完成当天训练 | 系统（勾完 / 训练会话结束） | ✓ | ✓ |
| `moved` | 顺延到本周其他天 | 系统默认 / 用户手动 | — | ✗（从分母扣除） |
| `excused` | 豁免（生病 / 出差 / 受伤 / 主动休息） | 用户选原因 | — | **✗（从分母扣除）** |
| `missed` | 未完成且未豁免 | 系统 23:59 结算 | — | ✓ |
| `rest` | 计划内休息日 | 系统 | — | ✗ |

**关键差异**：`excused` 是**从分母里扣掉**，不是"算一次失败"。计划 4 次、病假 1 天 → 本周目标变成 3 次，不是"3/4 不达标"。

---

## 3. 两个指标替代「连续天数」

| 指标 | 定义 | 放置 |
|---|---|---|
| **本周 N/M** | 本周已完成 / 本周目标（已扣豁免） | 今日 hero 主位 |
| **连续达标周** | 连续多少周达标；断一周归零 | 今日 hero 副位 + 日历顶部 |
| **累计训练天数** | 只增不减 | 「我的」与日历顶部 |

> 断一周只影响"连续达标周"，**不影响累计**。这样既保留激励，又不制造"全盘皆输"感。

---

## 4. 补记（backfill）

- 允许补记**过去 7 天内**任一天的训练（真练了但忘了记）
- 补记必须匹配当天的计划项，不能凭空加
- 补记条目带 `backfilled: true`：日历上有斜纹角标，统计正常计入，但**AI 引用时降权**
- 超过 7 天不允许：既防事后美化数据，也避免失真数据误导 AI 分析

---

## 5. 豁免额度（把"豁免"当信号，不当漏洞）

| 规则 | 值 |
|---|---|
| 每月自动豁免 | **2 次**（选原因即可，不再追问） |
| 超出后 | 需写一句原因（≤20 字），每月上限 **5 次** |
| 连续 3 个月用满 | 提示"计划可能排太满"，建议降级（4 练 → 3 练） |

原因枚举：`sick` 生病 / `travel` 出差 / `work` 加班 / `injury` 受伤 / `rest` 主动休息 / `other` 其他。

---

## 6. 结算时点与幂等

- **每日 23:59** 结算当天（启动时补结算遗漏日期）
- **每周一 00:00** 结算上一周 → 生成 `weekStats`、判定达标、更新 `weekStreak`、累加 `totalDays`
- 结算必须**幂等**：同一日期重复结算结果一致；补记后重算该周（`settleWeek` 可重入）
- 时区：一律用设备本地时区；跨时区旅行按当前设备时间，幂等保证不会重复计

---

## 7. 算法

```
settleDay(date):
  d = planFor(date)                       // 当天的计划项
  if d.excused            → 'excused'
  if d.moved              → 'moved'
  if !isTrainingDay(d)    → 'rest'
  doneGroups = setsDone(date)             // 训练会话的组数；无会话时用勾选数估算
  if doneGroups >= d.groups * 0.6 → 'done'   // 练一半也算，不让人白练
  if date < today         → 'missed'
  else                    → 'pending'

settleWeek(weekKey):
  planned = trainingDays − (moved 数) − (excused 数)
  done    = count(state == 'done')
  target  = ceil(planned * 0.8)
  eligible = done >= target
  full     = done >= planned
  weekStreak = eligible ? prev + 1 : 0
  totalDays += done
```

两个阈值各有理由：`0.6` 是"当天算完成"的组数门槛（练一半也算）；`0.8` 是周达标门槛（留出一次意外的空间）。

---

## 8. 与 AI 的关系

- 教练上下文带上：`本周 3/4 · 上周 2/4（含 1 次病假）· 连续达标 5 周`
- 豁免原因累计是**信号**：连续 3 周因 `work` 缺练 → 建议降到每周 3 练，而不是催他练
- 补记数据带 `backfilled` 标记，AI 引用时降权，避免"美化后的数据"污染判断

---

## 9. 边界与失败处理

| 场景 | 处理 |
|---|---|
| 未结算的历史日期 | 启动时批量补结算（按最早未结算日到今天） |
| 计划中途更换 | 按"当天生效的计划"结算，**历史不重算** |
| 手动改状态 | `done → excused` 允许（事后补假）；`missed → done` **不允许**，必须走补记 |
| 无训练会话但有勾选 | 用勾选条数估算组数，标记 `estimated: true` |
| 一周内换时区 | 按结算当时设备时区；幂等键用 `date + planId` |

## 11. 对 UI 的三处影响

1. **今日页 hero**：主位从「连续 12 天」改为「本周 3/4」，副位「连续 5 周」；累计放「我的」
2. **打卡日历**：每月每行右侧多一列周达标（`3/4 ✓`），点某天出「补记 / 标记缺席 / 查看当天」
3. **CTA 文案**：「完成今日打卡」→「记录今天」（打卡不再是一个动作，而是结算结果）
