# 中餐营养数据、食物解析与动态调整

- 日期：2026-10-22
- 回答四个问题：① 有没有专门算中餐热量的开源库 ② 能不能"说一句就出营养信息 + 给 AI 用的接口" ③ 按热量动态调整下一餐 ④ 训练计划按伤病/睡眠动态调整 + 身体状况预登记
- 关联：`docs/05-ui-design.md`（界面）、`docs/06-gap-analysis.md`（P0-1 饮食实际）

## 1. 中餐营养数据：现有开源资源

| 项目 | 规模 | 许可 | 接口形态 | 适合什么 |
|---|---|---|---|---|
| **[ruffood/cn-food-mcp](https://github.com/ruffood/cn-food-mcp)** | **~1724 种食物，25 项营养素/100g** | **MIT** | **MCP server**（`npx -y cn-food-mcp`），提供 `search_food` / `get_nutrition` / `compare_foods` / `filter_by_nutrient` / `list_nutrients` | **首选**。是"给 AI 用的接口"本身，不用自己包一层 |
| [Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data) | 1677 条，61 类，附 **GI 指数** | 仓库未标统一许可（数据源自公开出版物） | JSON / CSV / XLSX | **离线内置**的数据底，整包 ~几 MB，能塞进 APK |
| [ljunnan24-hash/recipe](https://github.com/ljunnan24-hash/recipe/) | **185 条真实食堂菜品**（含价格/估算热量） | 数据 **CC BY 4.0** | CSV / JSON / SQL | 参考"菜品级"数据长什么样；也可直接用作测试集 |
| [WellAlly-health](https://github.com/huifer/WellAlly-health) | 50 种食物，30+ 指标 | MIT | Claude Code skill | 参考**整餐自然语言解析**的实现（"燕麦粥 1 杯 + 鸡蛋 1 个"→ 汇总） |
| [LightMemo](https://kaiyuanbang.cn/zh-cn/repo/cclicking-lightmemo.html) | 离线 USDA SR Legacy + 中国食物成分表第 6 版 | 见仓库 | Android App | 参考"拍照→识别→匹配→**置信度 + 估重区间 + 数据出处**"的完整链路 |

**结论：数据不缺，缺的是"口语 → 结构"的那一层。** `cn-food-mcp` 解决"查得到"，解决不了"听得懂"。

## 2. "说一句就出热量"到底怎么做

三层，每层都可能降级，**输出必须带置信度与出处**：

```
"中午吃了碗牛肉面，还加了个卤蛋"
   │
   ├─ ① 切分与实体抽取（模型，输出结构化 JSON）
   │    [{name:'牛肉面', qty:1, unit:'碗'}, {name:'卤蛋', qty:1, unit:'个'}]
   │
   ├─ ② 匹配（三层降级，本地库优先）
   │    L1 精确/别名匹配      → cn-food-mcp search_food（豆腐 / 豆腐(北) 都能命中）
   │    L2 菜品拆解           → 牛肉面 = 面条 200g + 牛肉 60g + 油 8g + 汤（忽略）
   │    L3 相似替代           → 找不到时取同类别均值 × 烹饪系数
   │
   ├─ ③ 份量换算（单位词典）
   │    碗/份/盘/两/个 → 克；一律给区间（小碗 200 / 中碗 300 / 大碗 400）
   │
   └─ ④ 汇总
        { kcal: 720±120, protein: 38, carb: 86, fat: 22,
          confidence: 'estimate', source: ['L2 拆解:牛肉面', 'L1:卤蛋'] }
```

### 中餐的四个真实难点（决定精度上限）

| 难点 | 例子 | 差多少 | 处理办法 |
|---|---|---|---|
| **混合菜没有条目** | 宫保鸡丁、鱼香肉丝 | 成分表里只有原料级 | **拆解成原料 + 标准配方比例**（鸡胸 100 + 花生 15 + 油 10 + 糖 6） |
| **烹饪油不可见** | 炒青菜，油 5 g vs 15 g | 45 → 135 kcal，**差 3 倍** | **个人油量系数**：默认 8 g/份，用户校正 3–5 次后学习自己的"炒"对应多少油 |
| **份量口语化** | "一碗""一份""半盘" | ±40% | 单位词典 + 区间，取中位数并标 ± |
| **做法差异** | 鲈鱼 清蒸 105 / 红烧 190 / 油炸 280 | **2.7 倍** | 烹饪系数表 × 基础食材；抽问"怎么做的"（一句话可答） |

> 这就是为什么"直接让模型估热量"不可靠：**模型不知道你家一勺油是多少**。真正的精度来自"原料精确 + 个人系数校正"，不是更大的模型。

### 给 AI 用的两种接口形态

**形态 A：函数调用（推荐）**——模型自己查库，比自己背数字准得多

```jsonc
// 暴露给模型的两个工具（直接对接 cn-food-mcp 的语义）
search_food({ query: "牛肉" })        // → 候选列表 + 每 100g 营养
get_nutrition({ food_id: 285 })       // → 25 项营养素
// 模型流程：切分 → 逐个 search → 拿 id → 换算份量 → 汇总 → 自查合理性
```

**形态 B：一次性 HTTP 接口**——前端或第三方直接调

```http
POST /api/food/parse
{ "text": "中午吃了碗牛肉面，还加了个卤蛋", "at": "2026-10-22T12:30" }

200 OK
{
  "items": [
    {"name":"牛肉面","grams":450,"kcal":620,"protein":26,"carb":82,"fat":18,
     "confidence":"estimate","source":"L2:拆解","editable":{"oil":8}}
  ],
  "total": {"kcal":720,"protein":38,"carb":86,"fat":22},
  "confidence": "estimate",
  "followUp": "油多吗？"          // 只有在不确定性大时才问，且只问一句
}
```

**两种都要支持**：形态 A 给"教练对话"用（模型边查边说），形态 B 给"记录入口"用（点一下就落库）。

## 3. 按热量动态调整下一餐

### 3.1 输入与触发

```
触发：① 每次记录一餐后  ② 每晚 21:00  ③ 训练结束后（当天训练日）
输入：今日目标 / 已摄入 / 剩余餐次 / 蛋白缺口 / 今天是否训练日
输出：一条建议（不是改计划表），带一键采纳
```

### 3.2 规则表

| 场景 | 判定 | 建议 | 为什么 |
|---|---|---|---|
| 热量已超 10% 以内 | 剩余 < 100 kcal | 只建议补蛋白（无糖酸奶 / 蛋清），不补碳水 | 超一点不必焦虑，但蛋白缺口要补 |
| 热量超 20% 以上 | 剩余为负 | **不补偿**，只提示"今天多了，明天回到计划" | 补偿性节食是暴食循环的起点 |
| 蛋白缺口 > 30 g | 蛋白达成 < 80% | 下一餐加 1 份蛋白（给出克数） | 减脂期蛋白不足会掉肌肉 |
| 热量缺口 > 400 kcal（非训练日） | 吃太少 | 提示加餐，并说明"吃太少同样掉肌肉、影响睡眠" | 需要主动反对极端节食 |
| 训练日且缺口 > 300 kcal | — | 训练后 60 分钟内补 20–30 g 蛋白 + 40 g 碳水 | 补糖原窗口 |

### 3.3 三条红线

1. **单日超标不做次日补偿**——只把明天拉回计划值，不削减。
2. **日摄入永不低于 BMR**——任何"调整"都不能突破这条线（引擎算出的地板值）。
3. **一周调整不超过 2 次**——天天改计划会让用户觉得"这 App 没主意"。

## 4. 训练计划动态调整

### 4.1 信号与规则

| 信号 | 采集方式 | 触发阈值 | 调整动作 |
|---|---|---|---|
| **伤病 / 疼痛** | 动作详情「这个动作不舒服」 | 任意 | 该动作及**同模式动作**禁用 14 天；给 3 个替代（复用 §5.15 的换动作数据） |
| **睡眠不足** | 每日一行（或健康数据导入） | < 6 h | 当日**减量 25%**：减组数，**不减重量**（保强度、砍容量） |
| **主观疲劳** | 训练开始前 1–5 评分 | ≥ 4 | 同上；若连续 2 天 ≥4 → 整周 deload |
| **完成率下滑** | 近 2 周训练依从 < 60% | — | 计划降级（4 天→3 天），而不是催他练 |
| **连续训练过久** | 距上次休息 ≥ 10 天 | — | 强制插入休息日，文案写"恢复也是训练" |

### 4.2 推迟与"不欠账"原则

- 错过训练日 → **顺延**（把后面的训练日整体后移），**不累计欠账**。
- 明确不做"你已欠 3 次训练"这种提示——它制造焦虑，且增加受伤风险。
- 推迟超过 2 周 → 计划重置到上一周（降级），不是继续加。

### 4.3 交互

- 今日计划卡顶部一条浅色带：`今日已调整为 减量 25%（昨晚睡眠 5.2h）` + `[知道了] [按原计划]`
- **只提示一次**，用户选"按原计划"就记住，当天不再问。
- 所有调整写入 `sessions.adjustments[]`，供周复盘与 AI 教练解释"为什么这周轻了"。

## 5. 身体状况预登记（onboarding 2.0）

目标：**一次填写，生成可追溯的初始计划**。每步可跳过，但跳过要说明影响。

| 步 | 字段 | 为什么需要 | 跳过的影响 |
|---|---|---|---|
| 1 基础 | 性别 / 年龄 / 身高 / 体重 | BMR（Mifflin-St Jeor） | **不可跳过**，否则算不出热量 |
| 2 目标 | 减脂 / 重组 / 增肌 + 目标体重 + 期望周期 | 热量系数（−20% / −5% / +12%） | 默认"重组"，周期默认 12 周 |
| 3 经验与器械 | 训练年限 / 可用器械 / 每周天数 / 每次时长 | 动作库筛选、分化选择 | 默认新手 + 健身房 + 3 天 |
| 4 **伤病与限制** | 部位多选（膝/腰/肩/腕/颈）+ 严重度（偶发/影响训练/已就医）+ 备注 | 动作禁用表（见 §4.1） | **强烈建议填**：跳过则计划按完全健康生成，受伤风险自负 |
| 5 饮食限制 | 过敏 / 不吃（牛羊/海鲜/内脏）/ 宗教 / 素食程度 | 餐单硬过滤（不是偏好，是硬约束） | 默认无限制 |
| 6 作息与生活 | 睡眠时长 / 工作类型（久坐/站立/体力）/ 三餐时间 | 活动系数 + 餐次时间 | 默认 7h 睡眠 + 久坐 + 常规三餐 |
| 7 预览 | 展示：BMR / TDEE / 目标热量 / 蛋白 / 分化 / 禁用动作数 → 「生成计划」 | 让用户看到"填的东西真被用了" | — |

**可追溯**：计划卡上常驻一行 `基于 7 项输入生成 · 膝伤已排除 4 个动作`，点开可看完整输入。这样用户改体重后会知道"计划该重算了"。

> 这一条对 AI 也有用：教练每次对话都带上这份档案，它就不会建议一个膝伤用户去做保加利亚分腿蹲。

## 6. 落地顺序（与既有 P0 对齐）

| 步 | 内容 | 依赖 | 工作量 |
|---|---|---|---|
| 1 | 内置食物库（china-food-composition-data 1677 条 → 压缩 JSON，约 1–2 MB） | 无 | 0.5 天 |
| 2 | 三层解析器 + 置信度（L1 精确 → L2 拆解 → L3 相似） | 1 | 1–2 天 |
| 3 | 记录入口三档（照计划 / 一行字 / 常吃快选） | 2 | 1 天 |
| 4 | 摄入动态调整规则（§3） | 3 | 0.5 天 |
| 5 | 伤病与睡眠信号 + 训练调整（§4） | 无 | 1 天 |
| 6 | 预登记 7 步（§5） | 无 | 1 天 |
| 7 | 个人油量系数学习（用户校正 3 次后生效） | 3 | 1 天 |

**第 1–2 步是地基**：没有可靠的"口语 → 克数 → 热量"，后面所有动态调整都是在估算值上做微调，越调越离谱。

## 7. 已定决策（2026-10-22）

| # | 决策 | 结论 | 对实现的约束 |
|---|---|---|---|
| Q11 | 食物库形态 | **内置为主**（离线优先） | 数据以 `data/foods.v1.json` 随包发布；MCP 仅作可选增强，不在默认路径 |
| Q12 | 是否引 cn-food-mcp 代码 | **只要数据** | 查询层自研（约 200 行）；保留其字段语义（同 ID 体系便于将来互通） |
| Q13 | 拍照识别 | **不做** | 无相册/相机权限；记录入口只有文字与快选 |
| Q14 | 油量系数 | **后台学习，设置里可查看** | 不暴露配置项；校正数据存 `profile.oilFactor`，默认 8 g |

## 9. 我担心的三件事

1. **食物库的"看起来准"陷阱**：拆解估算能给一个精确到个位的数字（720 kcal），但真实误差 ±30%。UI 上**必须用区间或置信度标记**，否则用户会拿它当秤用，一有偏差就失去信任。
2. **调整规则的边际收益**：睡眠、疲劳这些信号需要用户每天录，录三次就烦了。建议只保留**伤病**为强信号（一次性、可长期生效），睡眠做成"可选一行"，不录就不调。
3. **中餐外卖是最大变量**：即便做了拆解，外卖的油与糖仍是黑箱。文案上不要给"精确"承诺，给"够不够用"的判断（蛋白够没够、热量大概在哪个档）更诚实。

| # | 问题 | 选项 | 建议 |
|---|---|---|---|
| Q11 | 食物库走"内置离线"还是"调 cn-food-mcp"？ | 内置（离线可用、体积 +2 MB）／npx 外部（需网络与 Node）／两者都留 | **内置为主，MCP 作为可选增强**（与"模型可选"的既有原则一致） |
| Q12 | 是否引入 `cn-food-mcp` 的代码？ | 它是 MIT，可引入 | 可参考其数据整备方式；但**我们只需要数据**，自己写 200 行查询层更可控 |
| Q13 | 拍照识别做不做？ | 做（需视觉模型）／只做文字 | **先只做文字**——拍照的失败率与校正成本都比文字高，且中餐拍照识别误差极大 |
| Q14 | 个人油量系数要不要显式暴露给用户？ | 显式（"你家一勺油约 8 g"）／后台静默学习 | **后台学习 + 设置里可查看**，不要让用户配参数 |
