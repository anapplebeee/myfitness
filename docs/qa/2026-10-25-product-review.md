# 产品经理评审：当前是否达到预期，以及优化方向

日期：2026-10-25；视角：PM/PO；方法：**实测行为**，不采信文档自述。
上位依据：[00 基线](../00-v1-baseline.md)（产品承诺）、[14 计划](../14-implementation-plan.md)（排期）。

## 0. 一句话结论

**核心闭环成立，但产品还"薄"——能记、能存、能看见进步，但留不住人。**

从"快速记下一组 → 可靠保留 → 看见进步"这条主线看，v1 已经跑通，且实测数据不错。但从"用户会不会第二天再打开"看，缺的是**首次使用引导、目标感、反馈节奏**这三样东西。技术完成度约 40%，产品完成度约 30%——后者更低，因为很多界面是"功能能用"而非"想用"。

## 1. 实测数据（不是估计）

在 390×844 视口、冷启动、清空存储的条件下测得：

| 指标 | 实测 | 判断 |
|---|---|---|
| 冷启动到可交互 | **143 ms** | 优秀 |
| 点"开始训练"后的输入框数 | **8 个** | 正确（预填上次重量） |
| 从点开始到记完一组 | **2.26 秒** | 达标（目标：单组 < 5 秒） |
| 记完后保存状态 | 显示"已保存" | 正确 |
| 今日页周进度 | `2/4` | 正确反映 |
| 断网后能否开始训练 | **能**，8 个输入框正常 | 核心承诺成立 |
| 断网后刷新 | 能恢复未结束的训练 | 核心承诺成立 |

**这组数据说明底层是扎实的**：本地优先、离线可用、录入快，三条都真的做到了，不是文档上写的。

## 2. 是否达到预期效果

### 2.1 达到预期的部分

| 承诺（00:24） | 现状 | 证据 |
|---|---|---|
| 快速记下一组 | 2.26 秒，预填上次重量 | 实测 |
| 可靠保留本次训练 | IndexedDB + 本地存储回落 + 墓碑删除 | 单测 + 实测 |
| 看见历史进步 | 教练页有容量、力量榜、动作趋势（+7%、+4%…） | 实测截图 |
| 无模型、无账号、断网可完成 | 实测断网可训练、可刷新恢复 | 实测 |
| 数据可导出、不锁定 | 导出/导入/备份/清空四件套 | 单测 + E2E |

**"看见进步"这块做得比预期好**：教练页虽无 AI，但"杠铃卧推 80kg × 7，+7%"这种表述对用户是有意义的，比空泛的"继续加油"强。

### 2.2 未达到预期的部分

| 问题 | 为什么是问题 | 严重度 |
|---|---|---|
| **无首次使用引导** | 新用户打开就看到 42 场"历史训练"（种子数据），会困惑"这是我吗"。且不知道该怎么开始 | **高** |
| **种子数据被当成真实数据** | 演示友好，但产品上危险：用户可能以为数据是自己的；导出时会带走假数据 | **高** |
| **无目标设定流程** | 用户不知道"我要练成什么样"。无目标就没有坚持的理由 | **高** |
| **无提醒/回访机制** | 没有通知、没有"你已 3 天没练"。留存完全靠自觉 | 中 |
| **教练页是静态统计** | 标题"进步来自可比较的记录"很克制，但用户期待的是"教练"——会失望 | 中 |
| **设置项过少** | 只有每周次数、身高、过敏原。没有单位偏好、提醒、数据清理策略 | 中 |
| **无"今天练什么"的决策辅助** | 今日页显示计划，但不解释"为什么今天练这个" | 中 |
| **错误恢复路径不明确** | 数据损坏/存储满时用户不知道怎么办 | 低 |

### 2.3 最该修的一条

**种子数据 + 无引导**是组合杀伤：新用户第一次打开，看到 42 场训练、289.5k kg 容量、力量榜——**这不是他的数据**。

产品上应该二选一：
- **A**：首次启动进入引导，明确"这是一份示例数据，可一键清空"，引导设目标、选模板；
- **B**：首次启动为空状态，用空状态引导代替示例数据。

当前是"既不引导也不清空"，最差的组合。这不是技术债，是产品决策缺失。

## 3. 是否脱离架构

### 3.1 符合架构的部分

| 架构要求（02） | 现状 |
|---|---|
| 领域纯函数，不碰 DOM/fetch/存储 | `domain/` 13 个文件，仅 `sync.ts` 含 `fetch`（传输层已抽象为接口，可注入） |
| 本地优先，IndexedDB + 回落 | 已实现，含 1500ms 打开超时 |
| 视图不持有可变 state | 用 `readonly` + computed，符合 |
| 派生值不落库 | 容量/PR/周完成数均实时计算 |
| 删除用墓碑 | `deletedAt`，且**快照保留墓碑**（防复活） |
| 内容包带授权与校验和 | 已实现并有 18 项校验测试 |

### 3.2 偏离架构的部分

| 偏离 | 性质 | 处置 |
|---|---|---|
| `SyncPanel.vue` 直接 `localStorage.setItem` 存密钥 | **真违规**：视图碰存储，且密钥属设备私有 | **已修**：移入 `store/deviceSettings.ts`，11 项测试 |
| `sync.ts` 在 domain 层含 `fetch` | 轻微偏离：传输层与纯逻辑混在一个文件（351 行） | 记录为技术债，建议拆 `sync-core` / `sync-transport` |
| `PlanView.vue` 791 行、29 个顶层函数 | 视图过重：周目标、日历、目标编辑、顺延、模板切换挤在一个文件 | 记录为技术债，拆分需配套 E2E |
| 无 lint / 无分支策略 / 无评审 | 工程流程缺失（非架构） | 见流程文档 §5 |

**判断：没有整体脱离架构，但有两处真实偏离，其中一处（密钥）有安全含义，已修复。**

### 3.3 一个更深的问题：契约与实现的距离

`docs/sync-contract.md` 写得比实现严谨得多。例如契约要求"三方合并 UI + 冲突副本持久化"，实现只有检测与提示；契约要求"7 天幂等记录"，实现有 TTL 但未测过期路径。

**这不是脱离架构，是"契约超前于实现"**。风险在于：后续接手的人会以为契约=现状。已在 12 号结果表逐条注明"未做"部分，缓解此风险。

## 7. 结论

| 问题 | 回答 |
|---|---|
| 是否达到预期效果？ | **核心闭环达到，产品体验未达到**。能记、能存、能看见进步，但留不住人 |
| 是否脱离架构？ | **未整体脱离**。两处真实偏离，密钥那条已修，另两处记为技术债 |
| 哪些需要优化？ | 首次引导（最急）、示例数据标识、目标设定、教练页正名、设置补齐 |

**下一步建议顺序**：首次引导（4.1-1）→ 模板与周目标 E2E（6.3-1/2）→ 目标设定（4.2-4）→ Android 链路。

理由：引导解决"第一眼信任"，E2E 解决"敢改"，目标设定解决"为什么坚持"。Android 虽重要，但在留存问题解决前打通只是把问题搬到手机上。

## 9. 第二轮：空状态与 E2E 补强（同日）

### 9.1 空状态（评审 §4.1 第 2 项）

实测发现的问题比预估严重：

| 页面 | 空状态表现 | 问题 |
|---|---|---|
| 教练页 | 大字 **0 kg**、**0 场训练**、空的"动作趋势"标题 | 用户会以为应用坏了 |
| 历史页 | **0 次**、**总容量** 与空列表 | 同上 |
| 今日页 | 已有"还没有训练记录"提示 | 可接受 |

处置：教练页与历史页改为**不显示任何 0**，直接给下一步动作。

- 教练页："还没有可比较的记录 / 先完成一次训练"，附解释"没有记录之前，这里的任何数字都没有意义，所以先不显示"
- 历史页："还没有训练记录 / 第一次训练完成后，这里会有东西"，按钮回到计划页

**为什么这样改**：`0 kg` 是"结果"，空状态该给"下一步"。数字为零不代表用户失败，只代表还没开始。

## 10. 第三轮：目标、训练对比、饮食 E2E、Android（同日）

按产品评审建议的四项全部执行。

### 10.1 目标设定（建议 §4.2 第 4 项）

新增 `src/domain/goals.ts`，三类目标：

| 类型 | 进度依据 | 易错点 |
|---|---|---|
| 体重 | 最近体重 vs 起始体重 | **减重方向**：不能直接用 当前/目标，否则进度反向 |
| 力量 | 该动作历史最佳单组重量 | 自重/计时类动作无意义，仅 `load_reps` 可选 |
| 频率 | 最近 4 周平均每周次数 | 只看本周会让周初显示 0 次，造成挫败 |

设计决策：

- **进度封顶 100%**，超额不给 1.2 这种值
- **反向变化进度为 0 而非负数**
- **刚设目标时文案写"从今天开始算"**，不只给一个 0%（否则像坏了）
- 频率用"最近 4 周平均"，避免周初挫败
- 校验拒绝无意义目标（差距 <0.5kg、>60kg、体重超 35–250kg）

### 10.2 训练后小结（建议 §4.2 第 6 项）

结束训练时的总结页新增"对比上次"：

- 找同训练日（`dayId`）的上一次，回退到同标题
- 显示组数、容量及百分比变化
- **首次记录说明"这是第一次，下次就能对比了"**，不显示空白或 0
- **变化为 0 时不显示"容量 +0%"**（噪音），直接说"与上次持平"

### 10.3 饮食记录 E2E（覆盖缺口）

5 项：四餐次与汇总、**"未记录不等于 0"声明**、食物库添加写入、手工记录、记录带日期。

**两次真实编译失败并修复**：

1. `Duplicate class kotlin.*`：Cordova 插件模块拉入 `kotlin-stdlib-jdk7/jdk8:1.6.21`，与 Capacitor 8 的 `1.8.22` 冲突。先移除无用的 cordova 模块（不够），再在根 gradle 强制对齐 1.8.22（生效）。

### 11.2 AC-C09 备份排除

原 Manifest 是 `android:allowBackup="true"`——WebView 的 IndexedDB 存着全部训练数据与同步口令，会被传到用户云端备份，与"数据只在本机"承诺冲突。

已改 `false`，并加 `backup_rules.xml` / `data_extraction_rules.xml`（覆盖 Android 11- 与 12+）。实测 APK 内 `allowBackup=0x0`。

### 11.3 同步冲突

此前：检测到冲突只弹提示，两个按钮都只关提示、不做事，`makeConflictCopy` 从未被调用——等于没实现。

现在：

- 冲突发生时**立刻把双方存成副本**（最多保留 5 份）
- **保留远端**：用远端快照覆盖本地，标记已解决
- **保留本地**：force 推送到远端，远端那份留在副本里
- **随时取回**：副本列表可单独取回远端版本
