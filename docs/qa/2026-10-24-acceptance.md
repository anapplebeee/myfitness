## 3. 发现的问题

### 3.1 P1 · G0 门禁被绕过（流程问题）

`git diff b0e1ba7 HEAD -- docs/00,02,09,11,12` 输出为空：**五个权威文档一字未改**。逐项核实 13 号列出的 7 项阻塞，全部仍存在：

| # | 阻塞 | 核实结果 |
|---|---|---|
| 1 | 内容清单缺失 | `docs/content/` 不存在 |
| 2 | `goalCreditConfirmed` 语义冲突 | 09:48 仍与 09:7、11:27 并存，未统一 |
| 3 | `computeWeek` 空值解引用 | 09:80 仍是 `K = min(goal.currentMinimumTarget, A)`，先解引用后判空 |
| 4 | `slotId` 未定义 | 11:51 只在使用处提及，无实体字段定义 |

影响：代码按我的理解实现了 `computeWeek`（先判空），但**文档仍是有缺陷的**，下一个人照文档实现会踩同一个坑。这是"代码对、文档错"的不一致，比两者都错更危险。

### 3.2 P1 · 验收证据链不成立

16 号规定 Test ID 形如 `T-T03-01D`，12 号要求每条 AC 有可追溯用例。实测：**测试文件显式引用 AC 编号 0 处**（67 条全未引用）。所有测试都在，但无法回答"A05 由哪个用例保证"。等于有测试、无追溯。

### 3.3 P2 · 已修复：周完成口径双源

`metrics.weekCompletion` 按会话数统计，与 09 号"被唯一满足的项目数"冲突。界面已改用 `computeWeek`，该函数成为死代码但仍有 2 条测试守护，会让后来者误以为它是权威口径。**已在本轮删除**，并留注释指向 `domain/week.ts`。

### 3.4 P2 · 已修复：热身组无视觉区分

详情页首组是 `kind: 'warmup'`（不计容量），但界面与工作组外观相同。QA 复核时最初误判"容量不刷新"为缺陷，查存储才确认是正确行为。已加"热身"徽标并淡化。

### 3.5 P3 · 文档与实现的口径漂移风险

`14-implementation-plan.md` 写 20 周 / 270 人日，实际本轮 4 个提交已覆盖 S1–S3 的大部分；计划未随实际进度更新。不影响当前交付，但会让燃尽图失真。
