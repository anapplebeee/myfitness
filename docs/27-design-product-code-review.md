## 一、UI / 美术视角

### 1.1 总体判断

视觉语言是**统一的**，不是拼凑出来的：黑-骨白-酸橙三色、大圆角卡片、
大字号数字、中文标题用 700 字重。这套语言放眼看像"设计过的产品"，
而不是模板堆砌。

但对照 Keep 这类商业 App，差距不在"好不好看"，在三个更具体的地方：
**信息层级、语义色、细节密度**。

### 1.2 已修问题（本轮）

| 问题 | 现象 | 处理 |
|---|---|---|
| 圆环变椭圆 | 360px 宽时 94×118，肉眼可见地扁 | `flex: 0 0 auto` + `aspect-ratio: 1` + 尺寸改 `clamp()` |
| 「空白训练」压过主动作 | 全宽黑底大字按钮，是整页最重的元素，但它是低频操作 | 降级为描边按钮 |
| 「今天」与「已豁免」同色 | 两个都用 `chip--sky`，一个该点、一个不用管，颜色一样 | 今天→深底酸橙（高强调），已豁免→中性灰 |
| 「v1」版本号 | 模板版本对用户没有意义 | 移除 |
| 动作列表截断无说明 | 只列 3 个动作，用户以为这个计划就 3 个 | 加「等 N 个动作」 |
| AI 卡片两个配置入口 | 头部「配置」+ 正文「配置模型」，同一动作两个按钮 | 未配置时只留正文主按钮 |

### 1.3 待办问题（按投入产出排序）

| 优先级 | 问题 | 说明 | 参考 |
|---|---|---|---|
| P1 | **酸橙承担了 7 种语义** | 主按钮、已完成、达标、强调文字、进度环、选中态、品牌 | Keep 用主色只做"行动"，状态色单独一套 |
| P1 | **105 处字号 < 11px** | 自动审计数据 | 商业 App 正文下限 12px，辅助 11px |
| P1 | **112 处触控目标 < 44px** | 同上 | Apple HIG / Material 都是 44/48 |
| P2 | 空状态只有文字 | 无记录时是一段说明 | Keep 有插画 + 一个明确按钮 |
| P2 | 图标风格不统一 | 部分是手绘 stroke SVG，部分是中文字符徽章 | 统一到一套 stroke 图标 |
| P2 | 转场无方向性 | 只有 fade，前进/后退手感一样 | iOS 式左右位移 |
| P3 | 无骨架屏 | 本地优先，加载快，影响小 | — |
| P3 | 食物无图 | 纯文字条目 | Keep 有菜品图 |

### 1.4 与 Keep 的具体差距

- **Keep 的首屏是"今天该做什么"**，不是数据总览。我们的今日页英雄卡
  占了近半屏，但最有用的一句"今天练什么"埋在卡片中部的小字里。
- **Keep 的每个数字都带对比**（比上周 +12%）。我们只有绝对值。
- **Keep 的动作有示意图/动图**。我们有 `ExerciseDemo`，但只在详情里。

### 1.5 与 SparkyFitness 的差距

- 它有 **17 种语言**、深浅色、可换主题色；我们只有中文 + 固定配色。
- 它有 **大量图表**（趋势、分区间统计）；我们只有 Sparkline 和力量榜。
- 但它的界面**信息密度过高**，像数据后台；我们更接近消费级 App。
  这一点上我们不该学它。

## 二、产品经理视角

### 2.1 各页面功能评估

| 页面 | 核心任务 | 现状 | 问题 |
|---|---|---|---|
| 今日 | 决定今天练什么并开始 | 完成度高 | 英雄卡信息密度低；本周节奏的日期格在深色下对比弱 |
| 训练 | 管理计划 / 查历史 / 找动作 | 功能齐 | 三合一导致每段都浅；动作库缺器械筛选 |
| 周目标 | 看本周安排、顺延、豁免 | 逻辑严谨（N/A/K 模型） | 概念多，新用户不懂"K"是什么 |
| 饮食 | 记今天吃了什么 | 顺手 | 无"常吃一键复制整餐"；无周/月营养趋势 |
| 教练 | 看进步、问 AI | 有对比与力量榜 | AI 卡片置顶，未配置时占首屏却无价值 |
| 我的 | 身体数据与设置 | 清晰 | 目标设定与身体数据分散在两个 tab |

### 2.2 值得借鉴（按价值排序）

| 功能 | 谁在做 | 为什么值得 |
|---|---|---|
| **休息倒计时后台通知** | Keep / Hevy / Strong 全都有 | 训练时锁屏，回来发现休息早过了。这是真痛点，不是锦上添花 |
| **周报/月报** | Keep、SparkyFitness | 训练 App 的留存靠"看得见的进步"，单次记录提供不了 |
| **动作替代建议** | Hevy | 器械被占时要能立刻换一个同等刺激的动作 |
| **器械筛选** | 全部竞品 | 我们 103 个动作只有肌群筛选，家里只有哑铃的人找不到动作 |
| **围度记录** | Keep、SparkyFitness | 体重之外的身体变化，减脂期比体重更能反映进展 |
| **训练时长统计** | 全部 | 我们有 startedAt/endedAt，但只显示不多维统计 |

### 2.3 不该学的

- **社交/好友/排行榜**：Keep 的核心是社区，但那需要运营与审核，且与"训练是自己的事"冲突
- **课程视频库**：内容成本极高，不是我们能做好的
- **AI 拍照识别食物**：需要视觉模型 + 食物库，准确率不够会砸口碑

### 2.4 产品建议（一句话）

> 现在缺的不是功能数量，是**"练完之后有东西看"**。
> 周报应该排在所有新功能前面。

## 三、开发视角（代码审查）

### 3.1 量化结论

| 指标 | 结果 | 评价 |
|---|---|---|
| `any` 类型 | **0** | 严格模式下没有偷懒 |
| `@ts-ignore` | **0**（2 处 `@ts-expect-error` 在测试里，故意构造非法数据） | 干净 |
| `console.log` | **0** | 干净 |
| `setInterval` 未清理 | **0**（2 处都有 `clearInterval`） | 之前修过一个 |
| `addEventListener` 配对 | 10 添加 / 6 移除 | 见下方分析，无真实泄漏 |
| 除零风险 | 2 处除法都有 0 值保护 | 干净 |
| 单测 | 1007 项 / 51 文件 | — |
| E2E | 88 项 | — |

### 3.2 监听器配对分析（结论：无泄漏）

未配对的 4 个是：
- `App.vue` 的 `hashchange`：匿名函数，应用生命周期内不销毁，可接受
- `useBackLayer.ts` 的 `popstate`：同上，单例
- `ai-client.test.ts` 2 处：测试内的一次性监听

`useEdgeSwipeBack` 4 个触摸事件全部在卸载时移除，`theme.ts` 返回取消订阅函数。

### 3.3 本轮修复的代码问题

| 问题 | 影响 |
|---|---|
| `AiCoachPanel` 重复 CTA | 同一动作两个入口 |
| `TrainView` 状态色与语义不符 | 「今天」和「已豁免」同色 |
| 训练日动作列表截断无提示 | 用户误判计划内容 |

### 3.4 架构层面仍存在的债

| 债务 | 说明 | 风险 |
|---|---|---|
| **CSS 变量语义过载** | `--lime` 同时是品牌色、成功色、进度色 | 中：改一处会影响一片 |
| **视图层测试薄弱** | `views/**` 单测 0%，靠 88 项 E2E 兜底 | 中：E2E 慢，反馈周期长 |
| **`tracking.ts` 分支覆盖 73%** | 时长/距离类模式的部分边界未覆盖 | 低 |
| **无错误边界** | 任何一个视图渲染抛错，整个 App 白屏 | 中：建议加 `onErrorCaptured` |

### 3.5 建议的下一步（工程）

1. 加 Vue `onErrorCaptured` 全局兜底，避免单页崩溃拖垮整个应用
2. 给 `views/**` 补几个关键路径的组件测试（今日页状态机、训练页分段）
3. 把语义色从 `--lime` 拆出来（`--action` / `--success` / `--progress`）
