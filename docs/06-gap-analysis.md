# 产品缺口分析（训练者视角）

- 日期：2026-10-22
- 视角：以一个每周练 3–4 次、练了几年、用过 Hevy / Strong / 纸质本的人来评
- 结论先行：**当前设计是一个"计划的浏览器"**——告诉你今天练什么、让你勾掉；但不在训练中帮你做决定，也不给你"练下去的证据"。训练者留下来只靠两件事：记录够快、进步看得见。这两件都还不够。

---

## 1. 按一次训练的真实流程找缺口

| 阶段 | 用户实际在做什么 | 现在支持 | 缺什么 | 优先级 |
|---|---|---|---|---|
| 决定今天练什么 | 看计划 / 临时改主意加练 | 部分 | 临时加动作、改计划不改模板 | P1 |
| 走进健身房，器械被占 | 找个替代动作 | ❌ | **一键换等价动作**（替代数据已有，没接入训练流） | **P0** |
| 训练中记录 | 单手、汗手、3 秒内完成一组 | 部分 | 超级组 / 递减组 / RPE | P1 |
| 组间休息 | 看还剩多久、掂量下一组加不加重量 | 部分（有倒计时） | **建议重量**（渐进规则算出的目标） | P1 |
| 破纪录那一刻 | 想知道"这是不是我最好的一次" | ❌ | **实时 PR 检测**（最强留存钩子） | **P0** |
| 练完 | 看今天练了多少、比上周如何 | 部分 | 总结只有绝对值，没有环比 | P1 |
| 记错了 | 事后改某组重量 | ❌ | 记录编辑（24h 内） | P1 |
| 次日 | 酸痛、睡眠、状态 | ❌ | 恢复记录（可选，别做成表单） | P2 |
| 每周 | 想知道到底有没有进步 | ❌ | **周复盘 + 力量曲线** | P1 |
| 减脂平台期 | 体重不动，想放弃 | ❌ | 围度 / 体脂 / 照片证据 | P1 |
| 吃饭 | **实际**吃了什么 | ❌ | **计划 vs 实际分家**（致命） | **P0** |
| 连不上的时候 | 数据到底存上没 | ❌ | 同步状态可见 | P1 |

## 2. 三个必须补的

### P0-1 饮食：计划与实际必须分家

**现状**：勾选餐次 = 完成。整个 AI 分析建立在"计划 = 执行"的假设上。

**真实**：外卖、聚餐、蛋白没吃够。真实摄入和餐单偏差 20–40% 是常态。

**后果**：这是全产品最深的坑——**AI 体检的结论会被假数据带偏**。它说"蛋白 150 g 达标"，实际只有 90 g；它说"热量缺口 20%"，实际缺口 5% 甚至盈余。用户看到体重不动，会认为"这 app 算得不准"，而不是"我没按计划吃"。

**设计要点**

- 饮食卡加一层"实际"，只给三个入口，**都不要打字超过一行**：
  - `照计划吃`（一键，默认）
  - `一行字`（"外卖黄焖鸡" → 模型估 kcal/蛋白）
  - `常吃快选`（最近 10 项 + 收藏，两个数字：热量、蛋白）
- **只记热量与蛋白**，不追碳水脂肪克数。精度换依从性。
- 数据层：`checkin` 存 `actual {kcal, protein, confidence:'exact'|'estimate'}`，与 `planned` 分开；分析用 actual，缺失时回落 planned 并**明确标注"按计划估算"**。
- 依从率拆两个指标：**训练依从率**（完成组数/计划组数）与**饮食依从率**（有实际记录的天数/总天数）。现在混在一起算，两边都不准。

### P0-2 实时 PR + 每个动作的力量曲线

**现状**：训练总结里有 PR 徽标（还是我上一轮才补的），训练中零反馈。

**真实**：破纪录那一秒是健身 App 唯一真正有效的多巴胺。Hevy 的 PR 提示、Strong 的奖牌，都是靠这个留人。

**设计要点**

- 完成一组立即算：同一动作、同重量次数↑，或 e1RM↑ → 轻震动 + 一行 `PR · 卧推 e1RM 76.5 kg ↑1.2`
- e1RM 用 Epley 或 Brzycki，两个公式都算、取保守值，**在动作详情里注明用的是哪个**（避免"数字对不上"的质疑）
- 每个动作一条 e1RM 折线（不是只有体重有曲线——训练者的核心 KPI 是力量曲线，不是体重）
- 反例保护：只做 1 组的动作不出 PR 提示（单组波动大，会让 PR 变廉价）

### P0-3 器械被占 → 一键换等价动作

**现状**：动作库里有 `alt`（替代动作）字段，但训练中进不去。

**真实**：晚高峰的健身房，卧推凳排队 20 分钟是常态。这是每个训练者每周都会遇到的事，而现在只能"跳过"。

**设计要点**

- 训练中动作名右侧「换」→ 弹出 3 个替代（同肌群 + 同动作模式 + 按器械条件过滤，数据已有）
- 选择后：**本组记录挂到新动作，计划本身不变**（下次来还是原动作）——这是关键，否则用户不敢点
- 若替代动作不在计划里，本次训练里新增一行，结束后可选"加入计划"

## 3. 该优化但不紧急

| # | 项 | 为什么 |
|---|---|---|
| 1 | 休息卡给"建议重量" | 现在只有倒计时，用户还要自己回忆加不加。渐进规则（线性/双重渐进）算一个目标值放卡上，`建议 62.5 kg` |
| 2 | 组类型：超级组 / 递减组 | SetStepper 目前只支持单一组；实际训练里 superset 很常见。加一个 chip 标记即可，不必做复杂编辑器 |
| 3 | 记录编辑（结束 24h 内） | 汗手记错是高频事。改完要让"总容量/PR"重算 |
| 4 | 周复盘卡 | 周日一张：完成率 / 总容量环比 / 体重变化 / 下周只改一件事。成本低、价值高 |
| 5 | 同步状态可见 | 自托管模式下，界面应常驻一行"上次同步 2 分钟前 · 0 待上传"。**数据信任比功能多寡重要** |
| 6 | 围度 / 体脂 / 照片 | 减脂平台期，体重不动但腰围降 —— 没有这个证据，用户会以为没进展 |
| 7 | 动作库扩到 80–120 | 44 个在第 3 个月必然撞墙（尤其器械条件变化时） |
| 8 | 周训练量分布（按肌群） | "本周胸 12 组、背 4 组"——防止练成圆肩。openGym 的三视图值得借 |
| 9 | 疼痛标记 | 某动作标记"膝盖不适" → 两周内自动降权/给替代。AI 能聊，但数据层没记 |
| 10 | Deload 建议 | 计划有 `weeks` 但没有 deload 逻辑；4–6 周后应主动建议降一周 |

## 4. 明确不建议做

| 项 | 理由 |
|---|---|
| 社交 / 排行榜 / 成就徽章 | 健身是私事。排行榜对新手的负向作用大于激励；打卡徽章是假动机，两周后失效 |
| 语音教练（TTS 口令） | 健身房噪音下听不清，成本高，且手机外放很尴尬 |
| 精确到克的营养数据库 | 维护成本极高，收益极低。一行字估算法反而更可持续 |
| 摄像头动作识别 | 角度、光线、遮挡都劝退，噱头大于实用 |
| 智能手表独立 App | 手机端没打磨好之前不做第二个终端 |
| 多人组队训练 | 需要实时同步与账号体系，与"数据在自己手里"的定位冲突 |

---

## 5. 冷静判断

**只补三件**：P0-1 饮食实际摄入、P0-2 实时 PR、P0-3 换动作。

补完这三件，它才从"计划浏览器"变成"训练搭子"——因为三件正好对应训练者最在意的三件事：

1. **数据是真的**（不是计划的复印件）
2. **进步看得见**（PR 与曲线）
3. **现场能应变**（器械被占不慌）

再往后才是 deload、恢复记录、周复盘、围度照片。

**还有一个隐性问题值得单独说**：现在的"完成率"把训练和饮食混在一个分母里（`完成 x/y 项`）。这会让两边都失真——练完全部动作但没记饮食，显示 60% 完成；只勾了三餐但没训练，也是 60%。这个指标必须拆成两个，否则它会一路误导 AI 分析。
