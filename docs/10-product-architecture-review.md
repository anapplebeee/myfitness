# 产品与架构评审：从计划原型到可持续使用的健身 App

评审日期：2026-10-23。依据：README、docs/02–09、现有前端、仓储、服务端与 Android 工程。本文是评审建议，不自动替代原有已定决策，不代表功能已实现。

结论：功能方向基本覆盖训练与饮食，但需求尚不能直接作为完整开发基线；架构的分层、本地优先和 Capacitor 方向合理，数据模型、同步可靠性与算法约束仍不足以支撑文档承诺的产品。建议先统一需求和领域模型，再实现完整训练闭环，随后接入实际饮食与经过验证的自适应热量。

## 1. 评审范围与证据强度

- 已检查需求、交互与架构文档，以及关键实现；对五个问题做了隔离 Node VM 复现，结果见第 8 节。
- 未运行真机、浏览器端到端、APK 构建和真实模型调用；静态工程存在不等于已经完成发布验收。
- 08 号文档的竞品价格、数量、性能与“市场唯一”等断言，本次没有逐项复核，不能直接用作定价或市场结论。
- 外部技术事实参考 MDN 与 MacroFactor 官方资料；本次没有做用户访谈，目标人群与指标属于待验证的产品假设。

## 2. 产品定位：需要收敛服务对象，不必继续堆功能

建议第一版优先服务：希望规律进行力量训练、兼顾减脂或增肌、主要吃中餐、重视离线和数据可导出的成年个人用户。

核心价值建议表达为：“在健身房快速记录，知道自己是否进步，用可解释的饮食趋势辅助调整。”AI 承担解析、解释和建议，不能成为唯一入口。

需要区分两条用户路径：

| 人群 | 核心任务 | 第一版应该支持 |
|---|---|---|
| 初学者 | 不知道怎么开始 | 少量审核过的入门模板、清楚的动作文字要点、容易调整的训练安排 |
| 已有训练习惯者 | 已有计划，希望记录更省事 | 自建/复制模板、上次记录、快速完成一组、事后更正、历史趋势 |

“不登录”和“自托管”可以保留。普通用户应能直接离线使用；自行部署不应成为首次训练的前置步骤。买断、自带模型 Key、后续可选托管是不同商业决策，现有文档不足以证明用户愿意为其付费。

## 3. 当前覆盖与实际缺口

| 能力 | 当前实现 | 文档规划 | 评审判断 |
|---|---|---|---|
| 档案与目标 | 基础身体、训练、器械与饮食偏好 | 增加伤病、限制、首启重做 | 需定义适用人群、字段校验和可跳过路径 |
| 计划 | 本地规则/模型生成，导入 7 天日程 | 模板优先 | 需模板自建编辑、版本、生效日期和历史快照 |
| 训练执行 | 动作条目勾选 | 逐组、计时、PR、替换、恢复 | 核心训练闭环仍待建设 |
| 饮食 | 配餐计划与餐次勾选 | 实际日志、解析、置信度 | 必须把实际、计划和缺失分开 |
| 进步反馈 | 体重趋势、混合事项完成率 | 力量趋势、周复盘、训练量 | 需要统一统计单位和历史修订规则 |
| 打卡 | 有记录即算打卡、连续天数 | 周口径、顺延、豁免、补记 | 规则存在逻辑矛盾，需先重写规范 |
| 热量算法 | 静态公式与系数 | 自适应 TDEE | 可研究上线，但不能按“第 3 周自动接管”直接承诺 |
| 数据 | localStorage、整份 HTTP 状态、JSON 导入导出 | 迁移、冲突检测、更多导入 | 有原型，缺可靠性闭环 |
| 交付 | Web/PWA 文件与 Android 工程 | Android 优先、完整状态设计 | 缺真实安装、升级、进程恢复与离线验收 |

### 3.1 必须补齐的业务需求

1. **不填饮食资料也能记训练。**首次开始训练不应强制填写全部身体信息；到需要计算热量时，再补必要字段。
2. **训练会话生命周期。**明确开始、进行、暂停、恢复、结束、放弃；切后台、锁屏、杀进程、跨午夜后的行为；允许在训练中查看其他信息后返回。
3. **逐组事实记录。**重量、次数、时长、距离分别适用哪些动作；区分热身/工作组、未完成/跳过、单侧/双侧、单只哑铃/总重量、自重/负重/辅助重量、kg/lb。
4. **渐进规则。**首次重量由用户选择；基于历史给可解释建议，支持最小加重量、重复区间、未达标时保持。模板规则不能只剩动作名称和组次。
5. **计划编辑。**临时换动作只影响当前会话；修改未来计划要有生效日期。取消训练、重排、换模板不能删除已完成事实。
6. **无计划训练。**临时训练、旅行训练和手动添加的动作都应可计入历史；是否满足某个计划目标，另行匹配。
7. **实际饮食更正。**编辑、删除、复制、常吃快选、手工直接填热量与蛋白、无模型时记录。增加全天记录完整度，部分记录不等于全天摄入。
8. **事后修订。**不要无依据限制训练记录只能在 24 小时内修改、真实训练只能补录 7 天。补卡窗口可单独保留，但事实记录应允许更正并记录修改时间。
9. **可恢复的数据管理。**导入预览、单位映射、重复检测、失败回滚、导出恢复；删除在远端、副本和备份中如何生效，需要清楚说明。
10. **适用范围和限制。**先明确是否仅面向一般健康成年人；特殊健康状况的自动方案要有独立处理路径。过敏作为配餐硬约束，不能因为缩短首启流程而默认已经确认“无限制”。

### 3.2 调整既有设计的优先级

- 实时 PR 很有价值，但优先级应在正确记录、恢复与历史不丢之后。
- PR 应来自可比较的历史工作组；定义首次基线、重复提示、历史编辑后重算和不同器械不可直接混比。不要以“当天只练一组”为理由一律禁止真实 PR。
- e1RM 属于估算；需要定义支持的动作、重复范围、公式版本，不能默认所有高次数、自重、辅助动作都可比较。
- 模板不必先追求 6–8 个知名体系：先做少量规则完整、可验证、适合目标用户的模板，再逐步增加。
- 动作库数量不是验收指标。应先覆盖模板、器械条件和替代路径；保持稳定动作 ID。
- 无视频可作为既定范围，但初学者仍需可用的文字指导与风险提示，不能把“动作素材后补”误当成指导内容也可后补。
- 深色模式、BLE、社交、插件平台继续后置。竞品 CSV 导入有迁移价值，但支持几种格式应由目标用户来源决定，不宜宣称为全部商业 App 的统一门槛。

## 4. 周打卡模型需要修订

09 号文档的方向值得保留：允许灵活安排，区分休息和未完成，以周观察习惯。但当前算法会产生以下问题：

| 问题 | 具体反例 | 建议 |
|---|---|---|
| 顺延从分母扣除 | 原计划 4 次，一次移到周六后目标只剩 3 次 | 顺延只修改安排日期，保留同一个计划发生项 ID，不减少训练目标 |
| 完成数量可能重复计 | 同一次训练在原日期和补练日期都被归入统计 | 一次会话至多满足一个计划发生项；一天两次训练与训练天数分别统计 |
| 所有目标被豁免 | planned=0，done=0，算法得到 0>=0，本周自动达标 | 标为“休整/无目标周”，不新增达标周；是否保持既有连续周作为显式产品政策 |
| 周结算不幂等 | 每次重算都执行 totalDays += done | 总量从唯一会话/日期事实派生；周结果替换写入，不能重复累加 |
| 80% 不等于可少练一次 | N=2、3、4 时 ceil(N×0.8) 仍然等于 N | 明确解释实际效果；如需弹性目标，单独定义最低目标和理想目标，不用模糊宣传 |
| 60% 组数自动“完成” | 10 组练 6 组即与全部完成同状态 | 将“记录过训练”“计划完成度”“周目标达成”分开；阈值应可解释、可调研 |
| 日期状态混杂 | moved 是安排变化，excused 是目标调整，done 是执行结果 | 拆成计划状态、执行事实、派生统计三个维度 |
| 跨时区不稳定 | 同一会话在不同时区可跨日期、跨周 | 保存 UTC 时间、发生时区和稳定业务日期；切换设备时区不自动重归历史 |
| 无计划训练不能补记 | 真实周末训练不在当天计划中，被拒绝 | 事实允许记录，计划匹配与打卡资格另算 |

建议模型：`PlannedOccurrence(id, planVersionId, originalDate, scheduledDate, status)` 与 `WorkoutSession(id, occurrenceId?, startedAt, timezone, localDate, ...)` 分开。周统计是对二者的派生查询。

“四态”文档实际还包括 rest 和 pending，应明确完整状态集合及转换表。计划中途调整，要保存当时目标版本，并明确补记后重算哪一周以及后续连续周。

病假/伤病不宜因每月豁免额度用完而被阻止记录。可以单独记录原目标、调整后目标、调整原因；频繁调整时建议重新规划，而不是限制真实情况的表达。补录时间晚不等于事实不可信，不应仅因 backfilled 就自动降低 AI 权重。

## 5. 饮食和自适应热量：先解决数据有效性

当前把自适应 TDEE 提升为产品重点是合理的候选方向，但 08 号文档给出的简单公式只能作为实验基线。

建议规范：

- 日摄入区分 `missing / partial / complete / confirmedFasting`；计划值只能用于参考展示，不可自动回填为已摄入参与估计。
- 食物日志记录来源、估算/称量方式、单位、生熟状态、可食部分、数据版本和用户修订。`exact` 容易造成绝对精确的误解，建议使用可说明的来源类型。
- 不直接沿用“缺失摄入以前值补齐”；不完整饮食记录会系统性扭曲热量估计。MacroFactor 官方同样明确区分缺失与部分记录，并在数据不足时暂停更新。[资料](https://help.macrofactorapp.com/en/articles/74-expenditure-version)
- 算法需要冷启动、数据不足、可用、暂停几个状态；不能到第 3 周无条件接管。数据覆盖门槛需用本产品回放测试确定，不能照搬竞品门槛作为有效性证明。
- 体重短期变化受水分等因素干扰，固定 7700 系数与短期斜率不能证明真实消耗；展示“基于记录的估计”，不要承诺精确到 50–100 kcal。
- 固定漏记会使估计偏移，不能宣称趋势算法自动恢复真实摄入或真实 TDEE。可观察趋势与绝对精度是不同指标。
- 输出保留 `algorithmVersion / inputWindow / coverage / previousValue / proposedValue / reason / acceptedAt`，支持暂停、拒绝、回退与解释。
- 先用模拟与历史回放验证缺失、部分记录、体重突变、平台期等情况，再小规模观察。尚未验证前，保留静态估计与趋势展示。

07 号文档中的“睡眠不足一律不减重量”“疼痛统一禁用 14 天”“训练后 60 分钟窗口”“BMR 作为绝对摄入底线”等，不应直接变成普适自动处方。应建立依据、适用范围、停止条件与专业审核；本次不将其替换为另一套未经验证的数值。现有代码的固定性别热量下限与文档 BMR 下限也需要统一。

过敏排除、禁用动作、器械匹配应由确定性校验完成，不能仅靠提示词。食物库仓库的代码许可与数据使用权应分别核验，不能仅据代码 MIT 判断数据可商业分发；现有文档也已标注某候选库许可不明。

## 6. 架构评审

### 6.1 可以保留的部分

- Web/PWA 与 Capacitor 复用领域和应用逻辑，适合当前记录型产品。
- 本地优先、离线可记录、JSON 可导出、模型可选，价值一致。
- 视图、应用、领域与基础设施分层，方向清晰。
- 单体应用和单个可选自托管服务足够当前阶段，无需微服务、消息队列或 CRDT。

### 6.2 应补充的结构

```text
视图：今日 / 训练 / 教练 / 我的
                  ↓ 命令、只读查询
应用服务：训练会话 / 计划安排 / 饮食记录 / 周复盘 / 导入导出
                  ↓
领域：记录与单位 / 模板与渐进 / 统计口径 / 营养目标 / 周结算
                  ↓ 通过端口调用
基础设施：本地持久化 / 同步 / 模型接口 / 设备生命周期 / 数据包
```

应用服务编排事务，领域计算不依赖 DOM、存储与真实时钟。`store.get()` 当前返回可变对象，视图可绕过编排修改数据；建议逐步改为只读查询和明确命令，避免万能 `update(fn)` 承载全部业务。

核心实体至少包含：`Profile`、`PlanTemplate`、`PlanVersion`、`PlannedOccurrence`、`WorkoutSession`、`SessionExercise`、`SetRecord`、`FoodLog`、`BodyMeasurement`、`Recommendation`。不要把这些事实都塞进 checkin。

每个可同步实体具有稳定 ID、修订版本和必要的删除标记；不要依赖数组序号作为模型动作或同步引用。训练快照保存计划组次及当时显示的动作信息，修改模板不会改变历史。

### 6.3 存储与同步

1. **localStorage 适合原型和少量设置。**训练事实与饮食日志建议使用支持事务的本地存储，Web 优先考虑 IndexedDB；原生需要时通过适配器使用 SQLite。IndexedDB 并不免除备份、存储清理和配额处理责任。
2. **本地写入成功后再提示已保存。**事务成功后触发远端同步；UI 区分本地保存失败、待同步、已同步、冲突。`save()->boolean` 无法表达异步结果，建议返回可等待的结果并订阅同步状态。
3. **离线待上传必须持久化。**保存业务变更和 outbox 的操作应有原子性；启动先恢复本地事实和待上传队列，不能直接拿服务器旧状态覆盖本地。
4. **当前阶段可以继续整份快照同步。**同时必须有修订号、条件写入、写入串行化、冲突保留双方副本的处理。之后有实际需求再改为实体级同步。
5. **If-Match 是检测，不是自动合并。**明确遇到版本冲突后的界面和恢复步骤；标准 HTTP 条件请求可以用 412，若用业务 409 则在契约中统一，不要混用。
6. **服务器首次无状态不是服务不存在。**先确认 health/协议；空白服务器建立初始状态，真正的静态站点才回落为纯本地。
7. **同一设备多个标签页也会冲突。**需要通知刷新/单写入协调或乐观锁；解决多设备前先覆盖这一场景。
8. **不要靠关闭页面兜底保存。**后台上传只是尽力而为；进程被杀后应从已提交的本地数据恢复。休息计时保存结束时间戳，前台恢复时重算。
9. **历史保留政策需重审。**会话 180 天、日程 90 天直接删除会破坏长期力量趋势与溯源。区分事实、派生日程、缓存与聊天；历史事实默认保留，必要时归档。

### 6.4 服务端与安全

- API Key 当前在 state 中，会进入服务端和普通导出。拆分业务数据与设备密钥；普通导出排除密钥，原生可通过系统安全存储适配器保存。只移到另一个 localStorage key 不能防御同源脚本读取。
- 默认监听 `0.0.0.0` 且无认证，会将整份状态开放给可访问该端口的网络设备。建议默认 loopback；手机连接所需的局域网模式应显式配置并有认证与部署说明。
- 静态文件应只从构建后的公开资产目录服务，使用允许列表；当前以源码根目录服务、只拦 data 和 server.js，不能形成足够明确的发布边界。
- `writeState()` 的固定临时文件在并发请求下可能互相覆盖/rename 失败。单进程也会发生异步写入交错，需串行事务；备份失败与磁盘失败应作为存储错误处理，不能都归为非法 JSON。
- 认证隔离需要服务端校验、作用域到路径的安全映射与权限测试；一个前端 ScopeResolver 或 Registry 不等于多用户支持已经完成。
- 自托管手机访问 `http://局域网IP` 通常不满足 Service Worker 安全上下文要求，不能直接承诺 PWA 离线安装；HTTPS 和 localhost 开发例外见 [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)。

### 6.5 AI、插件与工程选择

- 模型结果先做 schema、范围、单位与业务限制校验，再形成可审阅的变更；自然语言记录可用轻量预览和撤销，高影响计划/热量变更需明确采纳。
- `response_format: json_object` 只能约束部分输出形态，不能替代业务校验。现在 normalizePlan 主要修正格式和组数，没有形成完整的限制校验链。
- 增加超时、取消、重复请求防护、失败保留输入、模型能力差异处理；AI 请求外发哪些身体与饮食信息要向用户说明，“本地优先”并不等于使用模型时数据不外发。
- 保留实际需要的 Storage/Model/Platform 接口。身份、作用域可留契约草案，但 Hook 总线、动态插件和分享权限体系不必成为 v1 基础设施。
- 不必为换框架重写。建议引入最小构建、模块边界和可执行测试；TypeScript 可渐进加入。把“双击 index.html”作为可选便携模式，评估其成本，不宜让它阻碍模块化和可靠存储。
- Android 目录包含需维护的原生配置与代码，不能一概当可随时覆盖的生成物；www 才应视为构建产物。真机检查返回键、键盘、锁屏、计时恢复、存储和升级迁移。

## 8. 本轮复现与静态发现

复现方式：Node VM 加载现有 util/exercises/engine/core/repo/store，替身 localStorage、fetch 和 toast；不改业务文件，不请求真实服务器。

| 中 | `js/engine.js:37` targets | 示例男/30 岁/175cm/180kg/目标 170kg/久坐/减脂：目标 2640kcal，宏量折算 2977kcal；独立蛋白脂肪目标与碳水下限发生冲突，需约束求解或报告无可行解 |

下列为静态发现，未做真实并发/进程终止测试：

- GET 远端成功后 writeLocal(data)，没有先检查本地未上传变更，存在断网记录在重启后被旧远端覆盖的路径。
- HTTP 保存没有上传队列、持久化确认或请求排序，可能在连续写入和失败后丢失同步意图。
- 固定 state.json.tmp 无串行化；备份副本也不能替代冲突解决。
- JSON 导入只检查 profile 存在，缺少版本、结构、范围校验与事务回滚。
- `settings.apiKey` 在 state；普通 JSON 导出直接序列化整个 state。
- 仓库没有发现覆盖这些核心逻辑的持久化测试套件；Android 示例测试不能验证业务。旧文档声称的临时目录断言，本次无法据此确认当前版本通过。

## 9. 建议实施顺序与验收

| 阶段 | 工作范围 | 必须通过的验收 |
|---|---|---|
| A：需求与数据契约 | 统一版本范围、周规则、实体与单位、适用范围、迁移/同步协议 | 顺延、豁免、零目标周、改计划、历史补录、跨时区都有明确输入输出实例 |
| B：可靠训练闭环 | 本地事务、版本迁移、模板、逐组记录、上次记录、替换、计时、恢复、编辑与趋势 | 记录一组后一旦显示已保存，立即杀进程可恢复；改计划不动历史；重复结束无重复会话；编辑后统计一致 |
| C：真实饮食闭环 | 手工/快选/解析、来源与份量、记录完整度、每日与周展示 | 无模型可记；部分/缺失不当全天；更正和删除正确更新统计；限制条件由规则校验 |
| D：跨设备发布 | 初次同步、持久化 outbox、修订冲突、串行服务端、密钥分离、备份恢复 | 两端并发不静默覆盖；断网记录重启不丢；新服务首次写成功；失败状态可解释且可恢复 |
| E：自适应与交付验证 | 估计实验、数据充分性、暂停机制、建议采纳、APK/PWA 升级与隐私说明 | 回放覆盖异常和缺失；能解释和拒绝变更；安装/升级不丢数据；发布包不含密钥 |

B/C 可先形成单机版本；D 是对外承诺可靠多设备的前置条件；E 的算法部分可以独立延后，不必阻塞稳定记录工具的交付。先确认方案和验收，再估工期，避免沿用各文档中零散的“0.5–2 天”估计。

建议监测：首个有效训练会话完成率、二周/四周仍有训练记录的用户比例、已保存会话恢复成功率、每组记录操作次数与耗时、全天饮食记录覆盖率、同步冲突与失败恢复率。隐私优先产品可从用户自愿反馈和匿名聚合开始，不默认上传敏感训练/饮食明细；业务目标值需首批试用建立基线。

本轮建议：先做 A，并以 B 为首个交付闭环；不要先整体重写 UI，再发现记录、计划和统计的底层语义需要重做。
