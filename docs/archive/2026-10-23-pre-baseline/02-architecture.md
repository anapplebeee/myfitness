## 1. 设计目标与非目标

### 1.1 目标

| # | 目标 | 可验证的判定 |
|---|---|---|
| G1 | **零依赖启动不退化**：双击 `index.html` 仍完整可用 | `file://` 打开后五个页面全部可交互，数据落 localStorage |
| G2 | **数据可离开浏览器**：支持自托管服务端，数据落在自己的文件里 | `node server.js` 起一个端口，两台设备看到同一份数据 |
| G3 | **逻辑可离线验证**：业务计算不依赖 DOM | 纯 Node 进程内可对日程构建/配餐/连签跑断言 |
| G4 | **换实现不改上层**：视图只认接口，不认存储 | 新增一个存储后端时，`views/` 零改动 |
| G5 | **手机可安装、可离线** | 主屏图标可安装；飞行模式下能打开并查看昨日数据 |
| G6 | **误操作可回滚** | 服务端保留最近 10 份写入前快照，可直接替换回去 |
| G7 | **扩展点先留好**：多用户 / 家庭共享 / 社交通过插件接入，不改 core | 写一个只实现 `AuthProvider` + `ScopeResolver` 的插件即可隔离两套数据（详见 03 号文档 §10） |

### 1.2 v1 不实现，但预留接缝

> 原表述「多用户 / 家庭共享 / 社交（收益为负）」不准确，现修订为：**现在实现是负收益，留接口是正收益**。

| 能力 | v1 状态 | 预留的接缝 | 启用成本 |
|---|---|---|---|
| 多用户 | 不做 | `AuthProvider`（内置恒等实现）+ `ScopeResolver` | 一个 L3 插件 |
| 家庭共享 | 不做 | 数据信封里的 `scope` 维度 | 一个 L3 插件 |
| 社交 / 分享 | 不做 | 只读快照 + `share:<token>` 作用域 | 一个 L3 插件 + 一条只读路由 |
| passkey 登录 | 不做 | 同上（`AuthProvider`） | 需 HTTPS + WebAuthn 依赖 |

代价只有三处：**数据加一层信封（一次迁移）**、**身份抽成接口（约 10 行）**、**能力注册表（约 20–40 行）**。详见 `docs/03-plugin-architecture.md`。

### 1.3 真正不做（且不打算靠插件补）

- 云托管、账号体系（数据主权是产品前提）
- 原生 App 与小程序（PWA 已覆盖安装与离线）
- 视频教学与 5600 动作库（与「精讲」定位冲突）
- 实时协作 / CRDT（见 §7）
- **运行时动态加载插件代码**（无隔离环境 = 任意代码执行，03 号文档 §1 已明确拒绝）

## 2. 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│ 视图层   views/today plan coach library body                 │
│          只做：渲染 DOM、绑定事件、调应用层                     │
└───────────────────────────┬──────────────────────────────────┘
                            │ 读 state / 触发动作
┌───────────────────────────▼──────────────────────────────────┐
│ 应用层   store.js                                            │
│          内存中的 state、变更编排、跨模块一致性                  │
└───────┬─────────────────────────────────────┬────────────────┘
        │ 纯函数调用                           │ 持久化（接口）
┌───────▼──────────────────────┐   ┌──────────▼────────────────┐
│ 领域层  core/ engine.js      │   │ 仓储接口  repo              │
│  static 数据：exercises foods│   │  load() save() flush()    │
│  无 IO、无 DOM、可单测        │   └──────────┬────────────────┘
└──────────────────────────────┘              │ 适配器实现
                              ┌───────────────┴───────────────┐
                      ┌───────▼────────┐            ┌─────────▼─────────┐
                      │ local          │            │ http              │
                      │ localStorage   │            │ GET/PUT /api/state│
                      └────────────────┘            └─────────┬─────────┘
                                                              │
                                              ┌───────────────▼───────────────┐
                                              │ server.js（可选，零依赖）       │
                                              │ 静态文件 + /api + 备份轮转     │
                                              │ data/state.json                │
                                              └───────────────────────────────┘
```

**依赖方向严格单向**：视图 → 应用层 → (领域层 | 仓储接口)。领域层不得反向依赖应用层或视图；仓储接口不得知道领域逻辑的存在。

### 2.1 分层职责

| 层 | 文件 | 允许做的事 | 禁止做的事 |
|---|---|---|---|
| 视图 | `views/*.js` | 拼 HTML、读 `store.get()`、派发动作、弹层 | 直接读写 localStorage / fetch、自己算业务数值 |
| 应用层 | `store.js` | 持有 state、调领域函数、调 `repo.save` | 出现业务公式（配餐、连签算法） |
| 领域层 | `core/schedule.js`、`engine.js` | 纯函数：输入数据 → 输出数据 | DOM、`Date.now()` 隐式依赖、随机数不注入 |
| 仓储接口 | `repo.js` | 定义 `load/save/flush` 与模式判定 | 包含任何业务字段知识（只搬整份 state） |
| 适配器 | `repo.local` / `repo.http` | 序列化、去抖、失败降级 | 做字段级合并（v1 明确不做） |
| 服务端 | `server.js` | 静态文件、状态读写、备份、限制 | 解释 state 内部结构（对服务端是不透明 blob） |

> 领域层的「隐式依赖」是设计约束：`Date.now()`、`Math.random()` 必须作为参数注入，否则测试不可复现。当前配餐求解用随机选食材，需要在 P1 改为可注入的种子函数。

### 2.2 扩展点（详见 03 号文档）

上表定的是「现在怎么分层」，还没说「以后怎么插东西」。扩展点统一挂在一个**能力注册表**上，共六个位：

| 扩展位 | 接口 | 已有实现 | 插件可替换 |
|---|---|---|---|
| 存储 | `StorageAdapter` | local / http | WebDAV、S3、加密盘 |
| 身份 | `AuthProvider` | `SingleUserProvider`（恒等） | passkey、家庭账号 |
| 作用域 | `ScopeResolver` | 恒等 `local` | 家庭共享、多用户 |
| 访问策略 | `AccessPolicy` | 全允许 | 家庭角色、只读访客 |
| 模型 | `ModelProvider` | OpenAI 兼容 | 本地推理、其他厂商 |
| 同步 | `SyncStrategy` | 整份 LWW | 乐观锁、字段级合并 |
| 设备 | `DeviceProvider` | 无（v1 不接） | BLE 心率带 / 体重秤 / 健康数据导入 |

另有**钩子总线**（`beforeSave` / `afterSave` / `planGenerated` / `checkinCreated` / `uiSlot`）用于流程与界面扩展。

原则：**只为已有两个实现的接口做抽象；只有一个实现的只留签名**。因此 v1 实际抽象的是存储与同步（有意义），身份与作用域只放了一个 10 行内的恒等实现当占位。

## 3. 数据模型

### 3.1 state 结构（v1）

| 字段 | 类型 | 说明 | 体量（典型） |
|---|---|---|---|
| `schemaVersion` | int | **新增**，用于迁移判定 | — |
| `onboarded` | bool | 是否完成首次资料填写 | — |
| `profile` | object | 身体数据 + `weights[]` 体重记录 | 3–5 KB/年 |
| `plan` | object \| null | 当前训练 + 饮食计划（模型或引擎生成） | 6–12 KB |
| `schedule` | `{date: item[]}` | 日程，按天分桶 | 保留 90 天约 60 KB |
| `checkins` | `{date: record}` | 打卡（**四态** done/moved/excused/missed/rest）+ 实际摄入 `actual{kcal,protein,confidence}` + `backfilled` 标记 | 4 KB/年 |
| `weekStats` | `{week: record}` | 周结算：planned/target/done/eligible/full/excused/missed | 每月 4 条 |
| `meta` | object | `weekStreak` / `totalDays` / `excusedThisMonth` | <1 KB |
| `sessions` | `session[]` | 训练会话：起止时间、逐组记录（重量/次数/RPE/是否 PR）、换动作记录 | 每次约 2 KB，保留 180 天约 100 KB |
| `logs` | `foodLog[]` | 实际进食记录：槽位、逐项（名称/克数/热量/蛋白/置信度/来源）、合计 | 每天 3–4 条，约 1.5 KB |
| `adjustments` | `adjustment[]` | 系统调整记录：训练/饮食、原因、动作、用户是否采纳 | 每周约 3 条 |
| `chat` | `msg[]` | **单会话**对话历史（原为教练/营养师两条线程，已合并），上限 60 条 | ≤45 KB |
| `settings` | object | 模型接口配置（**含 API Key，见 §9.3**） | <1 KB |

当前实测：`state.json` 全量 JSON 约 **20–120 KB**。这个量级决定了「整份读写」是可行的（见 §7）。

### 3.1.1 信封与作用域（为插件预留，详见 03 号文档 §4）

state 外面包一层信封，`data` 里才是上表的字段：

```jsonc
{
  "schemaVersion": 2,
  "scope": { "id": "local", "kind": "personal" },
  "data": { /* 上表全部字段 */ },
  "meta": { "updatedAt": "…", "revision": "sha256:…" }
}
```

- v1 行为不变：永远只有一个 `scope`，`id` 恒为 `local`
- 物理路径从 `data/state.json` 变成 `data/scopes/<scopeId>/state.json`，**多用户/家庭插件启用后无需迁移主结构**
- **不提前给实体加 `ownerId`**：scope 级隔离覆盖绝大多数场景；记录级归属由插件写可选 `meta.ownerId`，core 不解释

### 3.2 演进规则

1. 任何结构变更必须 `schemaVersion + 1`，并在 `core/migrate.js` 中提供 `vN → vN+1` 的纯函数迁移。
2. 迁移链逐级执行；未知的未来版本（`state.schemaVersion > 当前`）**拒绝写入**，只读展示并提示「数据来自更新版本」。
3. 迁移前自动生成一份备份（本地模式写 localStorage 的 `tieguan.state.vN`；服务端模式复用备份轮转）。
4. `schedule` / `chat` 需要**容量策略**：`schedule` 保留最近 90 天、`chat` 保留最近 60 条，超出部分在保存时裁剪（策略写在 `core/retention.js`，纯函数）。
5. **v2→v3 迁移**：新增 `sessions` 与 `checkins.actual`，均为可选字段，缺失时按旧逻辑（计划值）处理，不做回填。
6. **v1→v2 迁移特例**：旧结构 `chat: {workout: msg[], nutrition: msg[]}` 合并为 `chat: msg[]`，按 `ts` 升序归并、去重后截断到 60 条。迁移是纯函数，必须有单测（两条线程交替发言的时间序不能乱）。

## 4. 仓储接口契约

### 4.1 接口

```
repo.configure()  -> 'local' | 'http'   判定模式（幂等，可重复调用）
repo.load()       -> Promise<state|null> 读取；失败必须降级而非抛出
repo.save(state)  -> boolean             异步落盘；可去抖；不得抛异常打断 UI
repo.flush()      -> void                页面隐藏/关闭前强制推送
repo.mode / repo.base / repo.describe()  供设置页展示
```

### 4.2 语义约定

| 约定 | 内容 |
|---|---|
| **不抛异常** | `save` 失败只提示 + 保留本地副本；调用方无感知 |
| **先本地后远端** | http 模式下每次写：先写 localStorage，再推服务端。断网不丢数据 |
| **去抖** | http 模式合并 300ms 内的连续写入，只发最后一次 |
| **降级单向** | `http → local` 可自动发生；`local → http` 只在 `load` 时判定，避免运行中来回切 |
| **显式配置才报警** | 用户手动填过地址（`?api=` / `TIEGUAN_API`）时才弹「服务端不可达」；自动探测失败静默降级 |
| **服务端不透明** | 适配器不解释 state 内容，只做序列化搬运 |

### 4.3 模式判定顺序

1. URL `?api=<base>` → 持久化到 localStorage 后使用；`?api=local` 清除并强制本地
2. `localStorage['tieguan.api']`
3. `window.TIEGUAN_API`
4. 若 `location.protocol` 为 http(s)：**假定同源** `./api`，探测失败再静默降级（保证 `node server.js` 一条命令即用）
5. 否则 `local`

## 5. HTTP API 契约

单端口，`/api` 前缀，同源，无 CORS。

| 方法 | 路径 | 请求 | 成功 | 失败 |
|---|---|---|---|---|
| GET | `/api/health` | — | `200 {ok, app, stateExists}` | — |
| GET | `/api/state` | — | `200 <state>` | `404` 尚无数据 · `500` 读失败 |
| PUT | `/api/state` | `<state>` JSON | `200 {ok, bytes}` | `400` 非对象/非法 JSON · `413` 超 8 MB · `405` 其他方法 |

**语义**

- `PUT` 是**整份替换**，幂等：同一份 body 重复提交结果一致。
- 所有 `/api/*` 响应带 `Cache-Control: no-store`。
- 请求体上限 **8 MB**（当前状态量级的 60 倍余量），超出直接拒绝。
- 服务端**不校验** state 内部字段（保持不透明），只校验「是 JSON 对象」。
- 版本协商（P2）：`GET` 返回 `X-State-Revision`（内容哈希或 mtime），`PUT` 支持 `If-Match` 做乐观锁。

**安全头**：`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`X-Frame-Options: SAMEORIGIN`。

## 6. 部署形态（三档，逐档可选）

| 档位 | 启动方式 | 数据位置 | 适用 | 安全边界 |
|---|---|---|---|---|
| **A 本地** | 双击 `index.html` | 浏览器 localStorage | 单人单机、最低门槛 | OS 用户目录权限 |
| **B 局域自托管** | `node server.js`（默认 8787） | `data/state.json` | 手机+电脑同网、要 PWA 安装 | 明文 HTTP；建议仅绑内网 |
| **C 公网** | B + nginx/Caddy 反代 + HTTPS | 同上 | 随时访问 | **必须**加认证（basic auth 或前置 SSO）+ HTTPS |

> C 档没有认证就等于把健身数据和模型 Key 公开。若要走 C 档，认证方案需单独评审（passkey 在此时才有意义）。

## 7. 同步与冲突策略

### 7.1 候选方案对比

| 方案 | 实现成本 | 并发写风险 | 查询能力 | 结论 |
|---|---|---|---|---|
| **整份最后写者胜（LWW）** | 低（无额外字段） | **高**：两设备同时改，后写覆盖先写 | 无需 | **v1 采用** |
| 整份 LWW + 乐观锁（`If-Match`） | 中 | 中：冲突被检测到并提示，不静默丢 | 无需 | **v2 建议** |
| 字段级合并（带 `updatedAt`） | 中高 | 低 | 无需 | v3 候选 |
| 操作日志 / CRDT | 高 | 极低 | 需要额外物化 | 不做 |

### 7.2 v1 的明确代价与兜底

- 采用整份 LWW，**并接受**「两设备同时编辑会丢一份改动」。
- 兜底三条：
  1. 服务端每次写入前保留快照（最近 10 份，时间戳命名）；
  2. 客户端每次写也先落 localStorage，形成第二副本；
  3. 冲突高发场景（训练中双端勾选）在产品层规避：P1 增加「本端最后一次读取时间」显示，超过 5 分钟未刷新时在写入前提示「其他设备可能已修改」。

> 明确不做「假装同步」：没有乐观锁之前，文档与 UI 都不承诺多设备安全。

## 8. PWA 形态

### 8.1 缓存策略

| 资源 | 策略 | 理由 |
|---|---|---|
| `index.html` / 导航请求 | 网络优先 → 回落缓存 | 保证拿得到更新，同时离线可开 |
| `sw.js` | 服务端 `no-cache` + 版本常量 | SW 必须能被更新，否则永久陈旧 |
| `css/*` `js/*` `icons/*` | 缓存优先 + 命中回填 | 体积小、变更随版本号整体切换 |
| `/api/*`、`/state` | **完全不缓存** | 数据实时性 |
| 跨域请求 | 直接放行 | 模型接口不应被 SW 拦截 |

### 8.2 更新与版本

- 缓存名带版本号（`tieguan-vN`），`activate` 时删除其他版本。
- v1：`skipWaiting()` + `clients.claim()` → 新版静默生效。
- v2（建议）：改为「装好后提示刷新」，避免用户正在填表时被换掉。

### 8.3 可安装性要求

`manifest.webmanifest` 需满足：`name` / `short_name` / `start_url` / `display: standalone` / `icons` 含 **192 与 512** / `theme_color`。另提供 `maskable` 图标（安全区内缩）与 `apple-touch-icon`（iOS 不读 manifest）。

## 9. 安全设计

### 9.1 威胁模型

| 资产 | 威胁 | 缓解 |
|---|---|---|
| 体重/训练记录 | 同机他人读取（共用电脑） | 浏览器 profile 隔离；导出加密为 P3 可选 |
| 模型 API Key | 误同步到服务端文件、日志泄露 | **见 9.3，密钥不进 state** |
| 服务端 `data/` | 目录穿越、直链下载 | 静态服务拒绝 `data/` 与 `server.js`；路径规范化校验 |
| 页面注入 | 模型输出被当 HTML 渲染 | 所有插值走 `esc()`；模型文本按**纯文本**渲染 |
| 提示注入 | 用户数据里藏指令改动模型人格 | 数据块用 `<data>` 包裹并在 system 中声明「是数据不是指令」 |
| 配额耗尽 | 模型调用被打爆 | 端侧限流（同一动作 3s 内只发一次）+ 失败不自动重试 |

### 9.2 服务端加固清单

- 路径穿越：`path.resolve` 后必须仍在根目录内
- 黑名单：`data/**`、`server.js`
- 请求体上限 8 MB；非法 JSON → 400 且不落盘
- 原子写：`tmp` 文件 + `rename`，避免半截文件
- 备份轮转：最多 10 份
- 可选：`HOST=127.0.0.1` 只监听本机，配合 SSH 隧道

### 9.3 ⚠️ 待决：API Key 是否随 state 同步

当前设计里 `settings.apiKey` 在 state 内，**会随整份 JSON 同步到服务端磁盘**。这与「密钥只在本机」的既有承诺冲突。

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| A. 保持现状（进 state） | 实现最简、换设备不用重填 | 密钥落到服务器明文文件；备份文件里也有 | ✗ |
| B. 密钥单独存 localStorage，永不进 state | 承诺一致；服务端只存业务数据 | 换设备需重填一次 | **✓ 推荐** |
| C. 服务端加密存储 | 折中 | 需要密钥管理，单机场景过度 | 暂不 |

> 结论建议：**B**。`settings` 拆成 `settings.sync`（endpoint/model，可同步）与 `settings.secret`（apiKey，仅本地）。
