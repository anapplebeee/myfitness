# 前端设计研究：训练记录类 App

日期：2026-10-25
目的：真机验证暴露了多处细节问题，需要以成熟产品为基准重新审视我们的界面。

## 0. 结论先行

对照商业产品与开源项目后，我们的**信息架构是对的**（今日/训练/周目标/饮食/教练/我的），
但**核心记录界面（LiveWorkout）的设计密度与信息组织落后于标杆产品**。

最关键的差距只有一条：

> **标杆产品在每一组都显示"上次这一组做了什么"，我们只在动作级别显示一次。**

## 2. Hevy 的设计要点（最有参考价值）

### 2.1 核心组件是"组表"（Set Table）

固定五列，全部用表格化数字（tabular figures）：

```
SET   PREVIOUS    KG     REPS    ✓
 1     60 × 10    60      10     ✓
 2     60 × 10    62.5     8     ✓
 3     60 ×  8    ——      ——
```

关键设计决策：

| 决策 | 理由（原文意思） |
|---|---|
| **Previous 列是必备** | "知道该打多少"是这类产品的核心价值 |
| 数字全部用 tabular figures | 9 变 10 时列宽不跳动，否则输入时表格会抖 |
| 组表做得**紧** | 一个动作要能在屏内看全，训练中不能滚动找 |
| 完成的组整行染绿（16% 透明度） | 一眼看出进度，不用读数字 |
| 动作名同时是**蓝色 + 粗体** | 既是标题又是"点击可换动作"的提示 |

### 2.2 单一强调色

Hevy 全产品只有一个动作色（Hevy Blue）。其余全是中性灰阶。

> 一个训练日志是在**组间的 2 秒一瞥**里被读的，所以配色必须让**数字**成为最响的东西。

这条对我们有直接启发：我们的 lime 绿目前同时用于「开始训练」「完成」「保存」「进度环」「标签页选中」——
**到处都是强调色，等于没有强调色**。

### 2.3 层级靠"表面阶梯"，不靠阴影

四层表面（画布 → 卡片 → 输入框 → 芯片）+ 1pt 描边。在近黑画布上阴影几乎不可见，所以用明度差表达层级。

### 2.4 即时反馈是核心

| 交互 | 反馈 |
|---|---|
| 勾选一组 | 120ms 填充 → 150ms 整行染绿 → 轻震动 → **自动开始休息计时** |
| 破纪录 | 金色 PR 徽章 220ms 弹入 + 轻震动（**不用彩带**） |
| 新增一组 | 行高 0→auto 200ms，单元格自动聚焦 |

### 2.5 动作时长

**120–320ms，且是功能性的**。"训练工具必须感觉即时"——不做装饰性动画。

## 3. Strong 的设计要点（极简派）

- 扁平中性灰画布，无卡片边框，靠间距分组
- 已完成的组填绿
- 一条**细长的自动运行休息计时条**（不是大卡片）
- 琥珀色 PR 标记
- 结论：**同一个信息，用更少的容器去装**

## 4. limelog（开源，技术栈相同）

- React 18 + Capacitor + TypeScript——与我们的选型一致
- 「全屏 lock in 训练视图」：训练时隐藏一切非必要元素
- 每组独立 RPE
- 说明：**Capacitor + React 完全能做出原生质感的训练记录界面**，我们不需要换技术栈

## 5. 我们的差距清单

按影响排序。

### P0：每组缺少"上次"参照

**现状**：只在动作标题下显示一次「上次 45 kg × 9 · 目标 4 组 × 8-10 次」。

**问题**：真实训练中每组重量不同（例如 1 组热身 60、2 组 80、3 组 85）。
只显示一个"上次 45×9"会让用户不知道**第 3 组该打多少**。

**标杆做法**：每一行显示该组上次的实际重量×次数。

### P0：完成按钮占位过大，没有可扫读的勾选

**现状**：每组右侧是「完成」文字按钮（约 72×46）。

**问题**：
- 一行里最宽的交互元素是"完成"，挤压了输入框
- 真机 369px 宽时，这正是导致「跳过」换行的原因
- 无法一眼扫出"哪些组已完成"

**标杆做法**：26–28px 方形勾选框，44px 触控区。整行染绿表示完成。

### P1：强调色泛滥

**现状**：lime 同时用于——开始训练、完成、保存、进度环、标签选中、Toast、目标进度条。

**问题**：没有"主次"，用户视线无处落点。

**标杆做法**：一个动作色，其余中性。

### P1：缺列头与对齐

**现状**：输入框靠 flex 自适应，宽度随屏宽变化。

**问题**：多组之间数字不对齐，扫读困难。

**标杆做法**：固定列（组号 / 上次 / 重量 / 次数 / 勾选），数字右对齐。

### P2：无 PR 反馈

**现状**：完成一组后只有「已保存本组」Toast。

**问题**：破纪录是这类产品最重要的情绪价值，我们完全没有。

### P2：休息计时是"大黑卡"

**现状**：整块深色卡片占屏幕上部大量空间。

**问题**：训练中它不该是主角，用户需要看到组表。
Strong 用细条、Hevy 用胶囊。

## 6. 本轮要改什么（按性价比）

| 优先级 | 改动 | 理由 |
|---|---|---|
| 1 | 每组显示「上次」 | 直接提升核心价值，改动局限在组行 |
| 2 | 完成按钮改为勾选框 | 同时解决换行与扫读问题 |
| 3 | 数字统一 tabular figures | 一行 CSS，消除输入跳动 |
| 4 | 收敛强调色，弱化次要元素 | 让主要动作重新突出 |
| 5 | 休息计时改为紧凑胶囊 | 给组表让出屏幕 |

## 7. 不改什么

| 项 | 理由 |
|---|---|
| 整体信息架构 | 研究显示与标杆一致，无需重构 |
| 品牌色 lime | 这是品牌资产，问题在**用量**不在色相 |
| 技术栈 | limelog 证明 React+Capacitor 足够 |
| 浅色主题 | Hevy 默认深色是因为健身房灯光；我们的浅米色画布在真机截图里表现良好 |

## 8. 无法验证的部分

**AVD 模拟器在本机无法启动**：x86_64 镜像需要 Hypervisor 驱动，安装需要管理员权限，
本会话已禁用审批弹窗。

替代方案：用浏览器在多个真机视口（360 / 390 / 412 / 430）做视觉与布局审计。
这能覆盖 CSS 层问题（本轮细节问题的绝大多数），但不能替代真机的：
- 触控手感
- 软键盘遮挡
- 系统手势冲突
- 真实 GPU 渲染差异

## 9. 本轮已落地的改动

| 改动 | 依据 | 结果 |
|---|---|---|
| 每组显示「上次」值 | Hevy / Strong 的 Previous 列是核心 | 已实现 `prevFor()`，按组索引取历史值 |
| 完成按钮 → 勾选框 | 标杆产品均为方形勾选 + 整行染绿 | 40px 方形，行内结构稳定 |
| 组行 flex → **CSS Grid** | flex 在 360px 会重叠 | 致命问题归零 |
| 数字 tabular figures | 避免 9→10 时列宽跳动 | 输入框已启用 |
| 「跳过」改图标 | 竖排文字占位且视觉吵 | 16px 图标 + 44px 触控区 |
| 小按钮触控区外扩 | HIG 44px | `::after` 外扩，视觉不变 |
