# 开发迭代流程

日期：2026-10-25；适用范围：本项目全部代码与文档变更。
上位依据：[14 计划](../14-implementation-plan.md) §3 治理、[12 验收](../12-v1-acceptance.md)。

## 0. 为什么需要这份文档

本项目已经出现过几类可以避免的返工，都源于流程缺失：

| 已发生的问题 | 根因 |
|---|---|
| 先写代码后补文档，多轮返工 | 没有"文档先于实现"的检查点 |
| AC 编号连续两次填错（AC-S01、AC-N02） | 填表前没查定义 |
| 测试跑在过期 `dist` 上，误判修复无效 | 没有"先构建再验证"的固定顺序 |
| 种子数据不落盘导致 datasetId 漂移 | 没有跨会话的回归用例 |
| 273 项测试长期靠人工执行 | 没有 CI 门禁 |
| Android 链路从未打通却一直列在计划里 | 完成状态没有可执行证据 |

这份流程的目标不是增加仪式，而是让这些问题**在发生前被拦住**。

## 1. 一次改动的生命周期

```
1. 确认需求与验收口径
   ↓  AC 编号必须先在 docs/12 里查到原文
2. 契约/文档先行（若涉及数据模型、协议、内容）
   ↓  G0 类阻塞未关闭前不开对应代码
3. 实现 + 单元测试（同一次提交）
   ↓
4. 类型检查 + 单测 + 构建（本地必须全绿）
   ↓
5. 需要界面验证的，补 E2E（不是一次性脚本）
   ↓
6. 更新文档：AC 状态、证据路径、已知限制
   ↓
7. 提交（一个逻辑改动一个提交）
```

## 2. 硬性规则

### 2.1 AC 编号必须先查后填

**规则**：任何在结果表或测试 `describe` 里写 AC 编号的动作，必须先从 `docs/12` 查到该编号的原文定义，复制到工作记录里，再写。

**理由**：本项目已连续两次把编号按自己的理解填写（AC-S01 被当成"快照哈希"，实际是"协议语义"；AC-N02 被当成"营养策略"，实际是"餐单快照"）。编号错的后果是追溯表失真，比没有追溯表更糟。

**检查方式**：提交前 grep 新增的 `AC-` 字样，逐条对照 12 号。

### 2.2 状态只允许四档，且必须带层级

| 状态 | 含义 | 允许的写法 |
|---|---|---|
| 未执行 | 没有任何验证 | `未执行` |
| 部分通过 | 部分层级已验证 | `部分通过（D 层）`、`部分通过（D+E 层）`，**必须注明缺什么** |
| 未通过 | 验证了但不满足 | `未通过（原因）` |
| 通过 | 全部层级 + 证据齐全 | `通过` |

**禁止**：因为"有代码"就推定通过；用"基本完成""差不多"等模糊表述。

### 2.3 测试分层与最低要求

| 层级 | 何时必须有 | 工具 |
|---|---|---|
| D 领域单测 | 任何纯逻辑（计算、规则、校验、过滤） | Vitest |
| C 契约测试 | 数据结构、协议、内容包授权 | Vitest |
| I 集成测试 | 服务端、存储、跨模块协作 | Vitest + 真实 HTTP |
| E 端到端 | 用户主路径（能点到的流程） | Playwright |
| R 内容评审 | 内容正确性、合规 | 人工签字 |

**门槛**：涉及界面的改动，如果没有对应 E2E，必须在提交信息里写明"未覆盖 E2E 的原因"。

### 2.4 验证顺序固定

```
typecheck（应用）→ typecheck（E2E）→ 单测 → 构建 → E2E
```

**理由**：曾因复用残留服务器导致测到过期 `dist`，浪费大量时间排查。`reuseExistingServer` 已固定为 `false`。

### 2.5 一个提交一个逻辑改动

允许：功能 + 它的测试 + 它的文档。
禁止：把"修 bug"与"重构"与"新功能"混在一个提交里。

**理由**：本项目曾需要逐个 worktree 验证历史提交能否独立构建，混合提交会让二分定位失效。

### 2.6 文档与代码同提交

代码改动影响以下任一内容时，文档必须在**同一提交**更新：

- AC 状态（12 号）
- 已知边界（17 号）
- 内容清单（content/README）
- 契约（sync-contract 等）

## 3. 每次迭代的检查清单

提交前逐项确认：

- [ ] AC 编号已从 12 号原文核对
- [ ] 新增逻辑有 D 层单测
- [ ] 涉及界面主路径的，有 E2E 或写明原因
- [ ] `npm run verify` 全绿（typecheck×2 + 单测 + 构建）
- [ ] `npm run test:e2e` 全绿
- [ ] 文档已更新（AC 状态 / 已知边界）
- [ ] 提交信息说明了"改了什么"与"为什么"
- [ ] 没有把设备私有数据（密钥）写进业务状态或快照

## 4. 评审要点

### 4.1 架构一致性

| 层 | 允许依赖 | 禁止 |
|---|---|---|
| `domain/` | 类型、其他 domain 纯函数 | DOM、fetch、存储、真实时钟（应注入） |
| `store/` | domain、repository、deviceSettings | 直接渲染 |
| `views/` `components/` | store、domain 纯函数、composables | **直接访问 localStorage / IndexedDB / fetch** |

**已发生的违规**：`SyncPanel.vue` 曾直接 `localStorage.setItem` 保存密钥。密码类数据属于设备私有，现已移入 `store/deviceSettings.ts`。

### 4.2 安全

- 密钥、token 不进 `AppState`（会被物化进同步快照）
- 密钥不进日志
- 导出文件不含密钥
- 同步错误信息不回显 token

### 4.3 数据正确性

- 删除用 tombstone，不用"从数组移除"
- 派生值不落库（容量、PR、周完成数）
- 时间统一 ISO 8601 带时区；重量统一克

## 5. 已知流程债

| 项 | 现状 | 影响 |
|---|---|---|
| 无 lint / prettier | 靠人工风格一致 | 低级问题靠 typecheck 兜底，覆盖率不足 |
| 无 CHANGELOG 自动化 | 手工维护 | 版本追溯成本高 |
| 无分支策略 | 直接在默认分支提交 | 多人协作时会冲突 |
| 无代码评审 | 单人开发 | 架构违规只能靠自查 |
| E2E 覆盖窄 | 16 项，三条主路径 + 过敏原 | 模板编辑、周目标、教练、设置无 E2E |
| 内容审核未执行 | 营养/过敏原标注为开发侧自测 | AC-N06 不能标"通过" |
